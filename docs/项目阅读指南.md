## 零、怎么读这份文档

**建议的三遍法：**

1. **第一遍（不求懂）**：按第四节的路线把文件过一遍，目标是"知道哪个文件负责什么"。遇到看不懂的语法直接跳过。

## 一、先建立地图

### 1.1 四个项目各自负责什么

```
DayManager.Core   ── 定义"数据长什么样"+ 纯算法（零框架依赖）
      ↑
DayManager.Data   ── 定义"数据怎么存进 SQLite"，以及所有查询
      ↑
   ┌──┴───────────────┐
DayManager.App      DayManager.Api
（Windows 界面，四个 Tab）（服务端：AI 代理 + 工具调用）
```

箭头方向是"引用"：`Data` 引用 `Core`，`App` 引用 `Data`。**引用是单向的**——`Core` 不知道 `Data` 的存在，这就是"分层"。

**为什么 `Core` 要单独一层、而且不引用任何框架？**

因为手机端、电脑端、服务端三方都要用同一份"一条日程包含哪些字段"的定义。如果各写一份，迟早出现"电脑上加了字段，手机上没有"——这类 bug 极难查。共用一份定义，从根上消灭它。

`Core` 里除了实体，还有 `Planning/` 下几个**纯函数**（`ReplyCleaner` 清洗 AI 回复、`PlanSpreader` 把任务摊到各天、`DurationText` 把分钟数说成人话）。放在这里的理由很实际：冒烟测试项目只能引用 `Data`，纯逻辑放在 `Core`/`Data` 才测得到；写在 MAUI 界面层就只能靠手点。

**四个界面（`App` 层）的分工：**

| Tab | 页面 | 回答什么问题 |
|---|---|---|
| 对话 | `ChatPage` | 唯一能操作所有数据的地方（核心） |
| 日程 | `MainPage` | 今天做什么，可以翻任意一天 |
| 大任务 | `ProjectsPage` + `ProjectDetailPage` | 那件大事推进到哪了 |
| 时间 | `TimePage` | 时间到底去哪了，我几点最在状态 |

**为什么 `Api` 不再是空的，而且不能省？**

最初后端只代理一次模型调用，客户端自己读写数据库。现在不行了，有两个硬理由：

1. **API key 绝不能放进客户端。** MAUI 打包出来的 exe 可以被反编译，密钥写进去等于公开。
2. **AI 要能主动提醒。** 客户端关着的时候也得能触发，逻辑只能在常驻的后端。

所以 `Api` 现在负责"调模型 + 拿工具改数据"（`AgentService` + `ItemTools`），客户端退化为显示层 + 手动操作层。

### 1.2 两条最重要的旅程

**A. 一次"打勾完成"**

```
① 你在界面上点圆圈
        ↓
② MainPage.xaml 里写着 Command="{Binding ToggleCompleteCommand}"
        ↓
③ 这一行让 MAUI 去调 MainViewModel 里的 ToggleCompleteAsync 方法
        ↓
④ ViewModel 调 _itemRepository.SetStatusAsync(id, Done)
        ↓
⑤ Repository 通过 DbContext 改数据库里的那一行
        ↓
⑥ 数据库返回新的 Item，ViewModel 更新界面的显示属性
        ↓
⑦ 界面自动刷新（因为属性变了会发出通知）
```

**B. 一句"把今天没做完的推到明天"**

```
① ChatPage 把这句话发给后端 /api/chat
        ↓
② AgentService 把它连同"当前数据快照 + 可用工具列表"一起发给模型
        ↓
③ 模型返回 JSON：一句回话 + 若干 actions（每个 action 对应一个工具调用）
        ↓
④ ItemTools 逐个执行，每改一条就把"改之前长什么样"写进 action_log
        ↓
⑤ 客户端拿到"改了哪几条 + 批次号"，刷新列表，并给出「撤回」
        ↓
⑥ 你点撤回 → 按批次号把那几条恢复成快照里的样子（冲突时提示，不硬覆盖）
```

B 这条链是理解这个项目的关键：**AI 不直接写数据库，它只能调工具；每个工具调用都要留痕**。这样才有"AI 改错了能撤回"这件事，也才敢让它改所有数据。

## 二、C# 语言基础（全部用本项目代码举例）

### 2.1 命名空间与 using

```csharp
namespace DayManager.Core.Entities;   // 声明"我属于这个命名空间"

using DayManager.Core.Enums;          // 引入别的命名空间，之后才能直接用里面的类型
```

分号结尾的写法（不是大括号）是较新的"文件级命名空间"，整个文件都属于它，省一层缩进。

命名空间可以理解为"姓氏"：`Item` 的全名是 `DayManager.Core.Entities.Item`。不写 `using` 就得写全名，太啰嗦。

### 2.2 类、属性、自动属性

打开 `Item.cs`，你会看到大量这种写法：

```csharp
public string Title { get; set; } = string.Empty;
public bool IsAllDay { get; set; }
public int? DurationMinutes { get; set; }
```

这叫**自动属性**（auto-property）。它一行顶三件事：

- `Title` 是对外暴露的属性名
- `get; set;` 表示可读可写
- 背后那个存值的字段由编译器自动生成，你不用写

为什么 C# 要这么设计，而不像 C++ 那样直接暴露成员变量？因为属性可以在将来加上逻辑（比如赋值时校验），而**调用方的写法完全不用变**。`item.Title = "x"` 这行代码，不管 `Title` 是简单字段还是复杂属性，长得一模一样。这是"为未来留后路"的经典手法。

`= string.Empty` 是初始值。给字符串一个空串而不是让它为 null，可以避免后面到处写判空。

### 2.3 可空类型 —— C# 里最容易误解的一处

项目里到处是 `?`，但**值类型和引用类型的 `?` 含义不同**：

```csharp
public DateTimeOffset? StartAt { get; set; }   // 值类型 + ? = "可能没有值"
public string? Notes { get; set; }             // 引用类型 + ? = "编译器请你提醒我它可能为 null"
```

- `DateTimeOffset` 是**值类型**（struct），本身永远有值（默认 0001 年），加 `?` 之后才允许"没有值"。数据库里对应"该列可以为 NULL"。
- `string` 本来就可以是 null。加 `?` 主要是给编译器的一个**声明**：我知道它可能为空，如果我忘了判空就警告我。

这套机制的目的很实际：**把"空引用崩溃"从运行时提前到编译期**。当你看到 `x.StartAt?.ToLocalTime()` 这种写法，那个 `?.` 就是"如果为空就整条表达式返回空，不往下走"——一行代码代替了三行 if。

相关运算符，项目里全都用到了：

| 写法 | 含义 | 项目里的例子 |
|---|---|---|
| `?.` | 为空就短路，不继续 | `_item.StartAt?.ToLocalTime()` |
| `??` | 左边为空就用右边 | `x.StartAt ?? x.DueAt ?? x.CreatedAt` |
| `??=` | 只在为空时才赋值 | `item.StartedAt ??= now;` |
| `is null` | 判空（比 `== null` 更可靠） | `if (item is null) return null;` |

`??=` 那一行特别值得记住，它在 `ItemRepository.SetStatusAsync` 里：

```csharp
item.StartedAt ??= now;
```

意思是"只在 StartedAt 还是空的时候写入当前时间"。如果用普通的 `=`，你手滑点两次"开始"，首次开始时间就被刷掉了——而这是算"启动延迟"的核心数据，**错了还没任何提示**。

### 2.4 枚举

`Enums.cs`：

```csharp
public enum ItemStatus
{
    Pending = 0,
    InProgress = 1,
    Done = 2,
    Cancelled = 3
}
```

枚举就是把"一组固定的取值"起上名字。数据库里存的是整数 0/1/2/3，代码里写的是 `ItemStatus.Done`。

**为什么显式写出 `= 0` `= 1`？** 因为不写的话编译器也会从 0 开始自动编号，但一旦将来有人在中间插入一个新状态，后面所有数字都会顺移——而数据库里已经存了旧数字，于是全部错位。显式写死是防止这种"改一行代码导致历史数据全错"的保险。

### 2.5 继承

```csharp
public abstract class SyncEntityBase   // 基类
{
    public Guid Id { get; set; }
    public int Version { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public DateTimeOffset UpdatedAt { get; set; }
    public DateTimeOffset? DeletedAt { get; set; }
}

public class Item : SyncEntityBase     // Item 继承它，自动拥有上面全部字段
{
    public string Title { get; set; } = string.Empty;
    // ...
}
```

`abstract` 表示"这个类只是个模板，不能直接 new"。

为什么要把同步相关的字段抽成基类？因为**以后新增的任何表都不该漏掉同步能力**。放在基类里，新建实体时 `: SyncEntityBase` 一写，这些字段自动就有了，不可能忘。

这也是"不要重复自己"原则的一个应用：规则只写一处。

### 2.6 表达式体成员 `=>`

```csharp
public DbSet<Item> Items => Set<Item>();
public Guid Id => _item.Id;
private static Color PrimaryTextColor =>
    Application.Current?.RequestedTheme == AppTheme.Dark ? Colors.White : Colors.Black;
```

`=>` 在这里表示"这个属性的值就是右边这个表达式"，等价于 `{ return ...; }`，只是短。

注意它和 lambda 表达式（下面会讲）用的是同一个符号，但在属性定义的位置上含义是"简写的 get"。

### 2.7 字符串插值

```csharp
parts.Add($"完成于 {completedLocal.Value:HH:mm}");
parts.Add($"逾期 {today.DayNumber - dueDay.DayNumber} 天");
```

`$` 开头的字符串里，`{...}` 内可以写任意表达式。冒号后面是格式（`HH:mm` 表示只显示时分）。

比 `"完成于 " + x.ToString("HH:mm")` 可读性好太多，这是 C# 里用得最多的语法糖之一。

### 2.8 集合与 LINQ

`ItemRepository.GetTodayListAsync` 里密集出现：

```csharp
var scheduledToday = db.Items.Where(x =>
    x.StartAt >= dayStart
    && x.StartAt < dayEnd
    && x.Status != ItemStatus.Cancelled);

return items
    .OrderBy(x => x.StartAt != null ? 0 : x.DueAt != null ? 1 : 2)
    .ThenBy(x => x.StartAt ?? x.DueAt ?? x.CreatedAt)
    .ThenBy(x => x.SortOrder)
    .ToList();
```

**LINQ**（Language Integrated Query）是一套用 C# 语法写"查询"的机制。`Where` 是筛选，`OrderBy`/`ThenBy` 是排序，`ToList()` 是执行并取出结果。

`x => ...` 这个叫 **lambda 表达式**，读成"对于每一个 x，做……"。`x` 的类型由编译器推断，不用写。

⚠️ **本项目最关键的一个坑就在这里**：`db.Items.Where(...)` 并不会在 C# 里执行，EF Core 会把整个表达式**翻译成 SQL 发给数据库**。所以不是所有 C# 写法都能用——翻译不了的就在运行时抛异常。详见第六节。

另一个重要区别：

```csharp
public ObservableCollection<ItemViewModel> TodayItems { get; } = new();
```

`ObservableCollection` 会在内容变化时**自动通知界面刷新**。换成 `List` 的话，你 `Add` 完界面纹丝不动——这是新手最常卡住的地方："数据明明加了，怎么界面没反应"。

`new()` 是"目标类型 new 表达式"，简写了 `new ObservableCollection<ItemViewModel>()`。

### 2.9 async / await

`ItemRepository` 里每个方法都是这样：

```csharp
public async Task<List<Item>> GetTodayListAsync(DateOnly? day = null, CancellationToken ct = default)
{
    await using var db = await _dbFactory.CreateDbContextAsync(ct);
    var items = await query.ToListAsync(ct);
    return items;
}
```

三个关键字：

- `async`：标记"这个方法里有等待"。
- `await`：**等待一个耗时操作完成，但不卡住界面**。执行到这里，方法会把控制权交还给调用方（界面继续能响应），等数据库返回后再接着往下走。
- 返回类型 `Task<T>`：表示"将来会给你一个 T"。`Task`（不带泛型）表示"将来会完成，但不返回值"。

为什么要有这套东西？因为访问数据库、网络请求这些操作可能要几百毫秒。如果同步等待，界面会整个冻住。对手机应用来说这是致命的。

`CancellationToken ct = default` 是"允许调用方中途取消"，好习惯，虽然现在还没用到。

`await using` 是 `using` 的异步版，表示"用完自动释放"（这里释放的是数据库连接）。

**`await` 会传染**：一个方法里用了 `await`，它自己就得标 `async`；调用它的方法也得 `await`……一路传到最上层。你会看到 `MainViewModel` 里所有命令方法都带 `async Task`，根因就在这。

### 2.10 partial（部分类 / 部分属性）

```csharp
public partial class ItemViewModel : ObservableObject
{
    [ObservableProperty]
    public partial string Title { get; set; } = string.Empty;
}
```

`partial` 意思是"这个类的定义可以分散在多个文件里，编译器会拼起来"。

这里有个更妙的用法：`[ObservableProperty]` 这个特性会让 CommunityToolkit 在**编译时自动生成** `Title` 属性的另一半实现——包括"值变化时发出通知"的逻辑。你只写声明，样板代码由工具补。

所以看到 `partial` 就要意识到：**这个东西的另一半不在你眼前，是工具生成的**。

（顺带说：老教程里常见的是 `private string title;` 加 `[ObservableProperty]`，让工具生成 `Title`。那种写法在 WinUI/AOT 下会报警告，现在推荐上面这种 partial 属性写法。）

### 2.11 特性（Attribute）

```csharp
[ObservableProperty]
public partial string Title { get; set; } = string.Empty;

[RelayCommand]
private async Task LoadAsync() { ... }
```

方括号里的叫**特性**，它给代码元素贴上元数据。本身不执行任何逻辑，而是被别的工具在编译期或运行期读取。

`[RelayCommand]` 会自动生成一个叫 `LoadCommand` 的属性（方法名去掉 `Async` 加 `Command`），于是 XAML 里可以写 `Command="{Binding LoadCommand}"`。手写这个本来要二三十行。

这类"用特性驱动代码生成"的做法在现代 C# 里非常普遍，它把重复劳动从你的指尖移到了编译器。

### 2.12 泛型

```csharp
public DbSet<Item> Items => Set<Item>();
private readonly IDbContextFactory<AppDbContext> _dbFactory;
public async Task<Item?> SetStatusAsync(...)
```

`<T>` 里的 T 是"类型参数"。`DbSet<Item>` 读作"装 Item 的 DbSet"。

好处是**一份代码适配多种类型，还保证类型安全**：`List<Item>` 里只能放 `Item`，放错编译就报错。对比一下没泛型时代的 `ArrayList`（什么都能放，取出来要手动强转，容易崩）。

`Task<Item?>` 读作"将来给你一个可能为 null 的 Item"。

### 2.13 接口

```csharp
private readonly IDbContextFactory<AppDbContext> _dbFactory;
```

`I` 开头是 .NET 的命名惯例，表示接口。接口只定义"能做什么"，不定义"怎么做"。

这里的好处是：字段声明成接口类型，以后换一种实现（比如换成内存数据库做测试）**不用改任何调用它的代码**。这就是"面向接口编程"。

### 2.14 异常与 try/catch/finally

`MainViewModel.LoadAsync` 里：

```csharp
IsBusy = true;
try
{
    var items = await _itemRepository.GetTodayListAsync();
    // ...
}
catch (Exception ex)
{
    await ReportErrorAsync(ex);
}
finally
{
    IsBusy = false;
}
```

- `try`：可能出错的代码
- `catch`：出错时怎么办
- `finally`：**不管出没出错都会执行**——所以 `IsBusy = false` 放这里，保证不会永远卡在加载中

`await using var db = ...` 和 `using var scope = ...` 也是同一类思路：确保资源一定被释放，哪怕中途抛异常。

### 2.15 static readonly

```csharp
private static readonly ValueConverter<DateTimeOffset, long> DateTimeOffsetToLong = new(...);
```

- `static`：属于类，不属于某个实例，全局一份
- `readonly`：只能在初始化时赋值，之后不能改

合起来就是"一个全局共享、且不会被意外改掉的常量对象"。这里用它是因为转换器是无状态的，没必要每次 new 一个。

## 三、.NET 与 MAUI 生态概念

### 3.1 项目文件与目标框架

`DayManager.App.csproj` 里：

```xml
<TargetFrameworks>net10.0-android</TargetFrameworks>
<TargetFrameworks Condition="$([MSBuild]::IsOSPlatform('windows'))">
    $(TargetFrameworks);net10.0-windows10.0.19041.0
</TargetFrameworks>
```

`TargetFramework`（目标框架）决定"这份代码编译到哪个平台"。一份源码编出两个平台的产物，这是 MAUI 的核心价值。

`net10.0-windows10.0.19041.0` 里那串数字是 Windows SDK 的版本号，不是随便写的。

### 3.2 NuGet 包

`dotnet add package Microsoft.EntityFrameworkCore.Sqlite` 做的事就是：从 NuGet（.NET 的包仓库，类似 Python 的 pip）下载库，并在 `.csproj` 里记一笔。

`.csproj` 是 XML，可以直接打开看，里面就是"我引用了哪些包、编到哪些平台"。

### 3.3 依赖注入（DI）

`MauiProgram.cs` 是启动时的一张"装配清单"：

```csharp
builder.Services.AddDbContextFactory<AppDbContext>(options =>
    options.UseSqlite($"Data Source={dbPath}"));

builder.Services.AddSingleton<ItemRepository>();
builder.Services.AddTransient<MainViewModel>();
builder.Services.AddTransient<MainPage>();
```

意思是"登记：谁需要东西，就从我这儿拿"。于是 `ItemRepository` 的构造函数里写个参数就能拿到数据库工厂：

```csharp
public ItemRepository(IDbContextFactory<AppDbContext> dbFactory)
{
    _dbFactory = dbFactory;
}
```

你从来没有写过 `new ItemRepository(...)`——是框架创建的。

**三种生命周期**（这是面试常问，也是实际会踩坑的地方）：

| 生命周期 | 含义 | 本项目例子 |
|---|---|---|
| Singleton | 整个程序共用一个实例 | `ItemRepository`（不持有业务状态，共用没问题） |
| Transient | 每次要都新建一个 | `MainViewModel`（持有"今天的清单"等状态，每次打开页面都该是干净的） |
| Scoped | 一个作用域内共用一个 | Web 里通常是一次请求 |

为什么 `MainViewModel` 不能用 Singleton？因为它存着"当前清单、输入框内容"。共用的话，第二次打开页面会带着上一次的旧数据。

### 3.4 为什么用 `IDbContextFactory` 而不是直接注入 `DbContext`

```csharp
await using var db = await _dbFactory.CreateDbContextAsync(ct);
```

`DbContext` 有两个特点：**不是线程安全的**（两处代码同时用会报错），而且**会缓存查过的数据**（长期共用一个实例，内存越滚越大）。

所以正确用法是"每次操作现开一个短命实例，用完即弃"。工厂就是干这个的。后面做后台采集线程时，这一点会变得非常关键。

### 3.5 EF Core：把 C# 对象变成数据库记录

| 概念 | 是什么 | 本项目对应 |
|---|---|---|
| `DbContext` | 一次数据库会话 | `AppDbContext` |
| `DbSet<T>` | 一张表 | `Items`、`Projects` |
| Fluent API | 用代码配置表结构 | `ConfigureItem(...)` 里那一串 `b.Property(...)` |
| 迁移（Migration） | 建表/改表的脚本 | `Migrations/` 目录 |
| 导航属性 | 表之间的关系 | `Item.Project` |

**迁移是必须理解的概念**：你改了 C# 类，数据库不会自己跟着变。迁移就是"把数据库从旧结构改成新结构"的脚本，有了它才能安全升级已有的数据库，而不是删库重来。

生成迁移的命令：

```bash
dotnet ef migrations add 名字 --project src/DayManager.Data --context DayManager.Data.AppDbContext
```

**`Migrations/` 里的文件是自动生成的，不要手改。** 要改表结构就改实体类，然后生成新迁移。

### 3.6 MVVM 与数据绑定

```
Model      = Item             数据，不知道界面的存在
View       = MainPage.xaml    界面，不含业务逻辑
ViewModel  = ItemViewModel    把数据翻译成界面能直接显示的样子
```

为什么不让界面直接绑定 `Item`？因为界面要的东西和数据库存的东西经常不是一个东西：

- 数据库里 `Status = 2`（整数）→ 界面上要显示"完成"和灰色
- 数据库里三个可能为空的时间字段 → 界面上要显示成一句话"逾期 3 天"

把这些格式化代码写进 XAML，XAML 会没法读；写进 `Item`，Core 层就被界面细节污染了。所以中间加一层专门做翻译，这就是 VM 的本职工作。

**数据绑定**的核心机制是 `INotifyPropertyChanged`：属性变化时发出一个"我变了"的通知，绑了它的控件自动刷新。你不需要写 `label.Text = xxx`。

`[ObservableProperty]` 就是让工具帮你实现这套通知，一个属性省十几行样板代码。

### 3.7 XAML 是什么

`MainPage.xaml`：

```xml
<Label Text="{Binding DateText}" FontSize="13" TextColor="Gray" />

<CollectionView ItemsSource="{Binding TodayItems}" SelectionMode="None">
```

XAML 本质是一棵**对象树**：`<Label .../>` 这一行等价于后台代码里的 `new Label { Text = "..." }`。

`{Binding xxx}` 读作"去 BindingContext 里找 xxx 这个属性"。`BindingContext` 在 `MainPage.xaml.cs` 里被设成了 `MainViewModel`，所以 `{Binding DateText}` 就是 ViewModel 里那个属性。

**`x:DataType` 一定要写**：

```xml
x:DataType="vm:MainViewModel"
```

加上它之后，如果你把属性名拼错（比如写成 `SummaryTxt`），**编译期就报错**；不写的话，要等到运行时才发现界面一片空白，而且没有任何提示。

## 五、本项目里"反直觉"的几个决定

这些是光看代码想不通、必须知道背景的。

### 5.1 时间全部存成整数

数据库里打开看，`StartAt` 是一串数字而不是日期。因为 EF Core 的 SQLite 提供程序**不支持比较 DateTimeOffset**——`Where(x => x.StartAt >= 今天零点)` 这种查询编译没问题，运行时直接抛异常。

改成存 Unix 毫秒后：整数能直接比大小，而且表示绝对时刻，顺带解决了跨时区比较的隐患。

**代价**：读出来的时间是 UTC，显示前必须 `.ToLocalTime()`。漏掉就会得到"看着对但差 8 小时"的结果，非常难查。`ItemViewModel.BuildSubtitle()` 里专门为此写了注释。

### 5.2 删除不是真的删除

`SoftDeleteAsync` 只把 `DeletedAt` 填上时间。因为真删掉的话，另一台设备同步时不知道"这条被删了"，会当成从来没存在过，于是又同步回来。

### 5.3 逾期任务自动滚到今天

`GetTodayListAsync` 里的第二类条件。理由很实在：**如果逾期的东西不自动滚过来，软件就等于帮你把它遗忘了**——恰好放大你说的"想着等下再做然后就拖掉"。而且界面上会显示"逾期 3 天"，让它赖不掉。

### 5.4 `StartedAt` 只写一次

`item.StartedAt ??= now;` —— 防止手滑点两次就刷新掉首次开始时间，那会让"启动延迟"数据静默失真且不可逆。

### 5.5 数据库位置写死在代码里

`MauiProgram.cs` 里：

```csharp
var dataDir = OperatingSystem.IsWindows()
    ? @"F:\DayManager\data"
    : FileSystem.AppDataDirectory;
```

之前用过环境变量 `DAYMANAGER_DATA_DIR`，后来删了。因为那制造了两个来源：从 bat 启动（有变量）和直接点 exe（没变量）会落到两个不同的库，表现为"清单突然空了"。

**教训：这类基础配置，单一来源比灵活重要得多。**

Android 上不能写死路径（没有盘符，且往任意目录写会被系统拒绝），所以必须走 `FileSystem.AppDataDirectory`。

### 5.6 使用时长只能"一次加一点"，不能用"结束 − 开始"

`UsageRepository.AddActiveSecondsAsync` 每次采样只把**这一次的采样间隔**加进 `DurationSeconds`。

如果用 `EndAt - StartAt` 算，得到的是"墙上的钟走了多久"，不是"人真的用了多久"：

- 人离开十分钟再回来用同一个软件 → 多算十分钟
- 合上笔记本八小时 → 多算八小时

而这份时长是干预引擎和 AI 排期的**唯一输入**。数字虚高，后面每一句"你今天该休息了"都建立在谎话上。

**这条能推广成一句更通用的话**：凡是"从数据里算出来的、将来要拿来下判断"的东西，都要问一句"它算的是我以为的那件事吗"。

### 5.7 采集在三个地方"切段"

`WindowsUsageTracker` 会在三种情况下结束当前会话、让下次自成一段：

1. 空闲超过 3 分钟（人走了）
2. 取不到前台窗口（锁屏、没有窗口）
3. 采样间隔突然超过 15 秒（睡眠、定时器被饿死）

前两种是为了不把"不在"记成"在用"；第三种是为了不让睡眠的八小时被摊进时长。

**为什么空闲是"切段"而不是"回头接着用同一条"**：时长是累加的，空档本来进不去；但"几点最有效率"那张柱状图是按会话的**起止区间**往小时桶里摊的。一条跨过午饭的会话会让柱子和总时长对不上——表现为"总时长 45 分钟，柱子加起来 1.5 小时"。

### 5.8 "人在不在"不能只看键鼠

判断人走没走，第一反应是"多久没碰键鼠"（`GetLastInputInfo`）。但看视频、看直播、听歌、打游戏的时候，人十几分钟不碰键鼠再正常不过——**偏偏是最该记的娱乐时长被整段丢掉**，只留下开头三分钟。于是"刷了两小时 B 站"在数据库里是 3 分钟，AI 会看着这份数据真诚地说"你今天很自律"。

所以 `WindowsUsageTracker` 在空闲超时之后还要再问两层，问得过就继续记：

1. 前台是不是"自己会往下走"的应用（`PassiveMediaApps`：播放器、音乐、游戏、客户端视频站）
2. 系统有没有声音在放（`SystemAudioMeter`，读 Core Audio 的电平表）

顺序是先查名单再读音频：名单是纯字符串比较，几乎不要钱；读音频要走 COM。

**为什么娱乐名单和这个名单要分开**：知乎、微博这类要一路滚动，三分钟不碰基本就是人走了（只是没关掉）。把它们也算"不用动手"，那就和挂机睡觉没区别了。

**接受的代价**：放着歌去睡觉会被记成"在用"。电脑确实在为你干活，而且锁屏那类情况已经由 `NotRealUsage` 排掉了。

### 5.9 AI 不能真删，撤销按批次

- AI 只能"标记放弃"（`Abandoned`），不能物理删除或软删。**放弃仍然出现在完成率的分母里**，这是刻意的：那样统计才诚实。
- 一次动作 = 一个批次 = 一个可撤单元。撤回是**永久可撤**的，而且界面上有独立入口、不经过对话（发现 AI 改错时，最不想做的就是再跟它聊一轮）。
- 碰撞到"你后来手改过"的记录时，提示而不是硬覆盖。

**为什么"用户自己的单条操作"没有撤销**：一步就能改回来，再给它做 undo 栈只会让两套撤销机制互相打架。

### 5.10 娱乐时长默认折叠

`TimeViewModel.IsEntertainmentShown` 默认 `false`。

回顾界面的第一原则是正反馈优先。一进来就把"你今天刷了两小时"摆在最显眼的位置，结果是人不敢打开这一页——而不看的统计等于没做。收起不是隐藏：按钮就在摘要卡片里，一次点击就到。

**这条和 5.6 是一对**：数据必须真实（5.6），但**呈现的顺序要照顾人的感受**（5.9）。真实和打击人不是一回事。

### 5.11 回车发送，Shift+回车换行

对话页的输入框：`Enter` 直接发送，`Shift+Enter` 才是换行。

**为什么这么定**：聊天界面（微信、Slack、Discord）的肌肉记忆就是"回车=发出去"。反过来定（回车换行、要点按钮才发）每发一句都要把手从键盘挪到鼠标，而这是这个软件里最高频的动作。换行是次要动作，所以放在要多按一个键的位置。

**为什么提示写在 Placeholder 里**：快捷键是看不见的。不写出来只有两种结果——多数人一辈子不知道能换行，或者按了回车发现消息发出去了才知道规矩。写进 Placeholder（而不是旁边加一行小字）是因为它有内容就自动消失，不占本来就紧张的输入区。

**最要紧的一关是输入法**：打中文时，拼音打完、候选词还没上屏的那段过程里，`Enter` 的意思是"就这个词"，不是"发送"。这时候把消息发出去，打一半的字连同候选框一起没了，发出去的还是一句谁也看不懂的半成品。这不是边角情况——**这个软件的主要输入方式就是中文**。实现里用 `TextBox` 的 `TextCompositionStarted` / `TextCompositionEnded` 跟踪组字状态，组字期间不拦回车（见 `Platforms/Windows/ChatPage.Windows.cs`）。

### 5.12 AI 的视野是"今天 + 7 天"，边界必须写进提示词

`AgentService.UpcomingDays = 7`。给模型的上下文里，除了今天的清单，还要带上**接下来七天**（每天都带 `id`，空的写「空」），并且明写一句：更早以前、以及这七天之后的安排你看不到，不知道就直说不知道。

**为什么必须有这一段**：最早只喂"今天"的清单，后果是用户问"明天有什么"，AI 答不出来。而这不是一个冷门问题——"接下来几天我有哪些事"是最常见的一类提问，人问它**不是为了回忆，是为了决定现在动不动**。答不出来的 AI 在这个场景里等于不存在。

**为什么是 7 天**：3 天撑不住"这一周"（周三不会知道周末）；30 天里绝大多数天是空的，白占 token，还会让模型在很远的未来上纠结。更远的以后走"按需查询"（让 AI 自己开口要某一天），现在先给够一周。

**为什么"你看不到什么"也必须写**：不给边界，模型就会补全。问"12 月 5 号有什么"，它宁可编几条也不说不知道——因为在训练里"我不知道"是低质量的回答。而**编造是这个软件里最坏的一类错误**：用户会照着它说的去安排，然后发现事情根本不存在，从此不再相信这个界面。

    实测（改完之后）：问"12 月 5 号我有什么安排"，回答是"看不到。我这边最远只到 11-03，12 月的安排不在我的视野里。"

**为什么空的一天也要写出来**：哪天是空的，和哪天有安排，同样是排期的依据。不写出来，AI 会把事情往最早的日子塞，表现为"每天都排满，而其中三天明明什么都没有"。空白是信息，不是省略的理由。

### 5.13 AI 偶发"空回复"：重试要分级，最后一次换姿势

上游（DeepSeek 推理模型 + `json_object` 模式）会**偶发**返回空内容——没有报错、`finish_reason` 正常，就是 `content` 一个字都没有。2026-10-27 用户连着三条消息都得到空回复；事后把同一句话原样重放八次，全部成功。**和输入无关，纯偶发**，上游也不会解释原因。

应对是三步，一次比一次用力（见 `AgentService` 调模型那段）：

1. 网络闪断、上游 429/5xx：隔半秒原样重发一次；
2. 内容为空：原样重试（赌偶发）；
3. 仍为空：**摘掉 `json_object` 模式再试**。提示词里本来就要求输出 JSON，模型多半还是会给；真给了纯文本，解析兜底也会把原话当回复带出来——比"没接住"强得多。

每一步失败都把 `finish_reason`、token 用量、requestId 落到 `logs/api-ai.log`（为什么必须落文件，见坑 19）。规律攒多了，才能从"偶发"变成"知道为什么"。

**为什么一天一天地查而不是新写一个范围查询**：一天该包含哪些条目是有讲究的（逾期未完成会并进今天、放弃的不出现），那套规则只有 `GetDayListAsync` 里那份是对的。再写一遍等于把规则抄第二份，而这类不一致的表现是"AI 说的和界面上看到的不一样"，极难查。七天就是七次查询，一个人用的数据量，换口径唯一是值的。

### 5.14 AI 缺信息时不弹表单，猜一句你会说的话放在输入框上方

字段从 `questions`（一组预填输入框）改成 `suggestions`（一排 chip，点一下就发出去），位置也从**回复下方**挪到**输入框上方**。

**改位置的起因是用户的一句抱怨**："这样我就看不到 AI 的回复了。" 追问的东西做成表单，会把自己说的话顶出屏幕——问完一句想看它怎么答，先看见三行要填的框。追问用嘴问就够了（`reply` 里一句话一个问题），那点信息量不值得占回话的位置。

**为什么改成"猜你会说什么"**：这里真正昂贵的是"组织一句话并打出来"，不是"问答对不对"。模型最擅长的恰恰是猜下一句。放四个按钮，他扫一眼点头就点，省的是最容易卡住的那一步。四个是上限（`SuggestionCleaner.MaxCount`），再多就换行把输入框顶没了——选择和要不要选，本身也是成本。

**为什么点一下直接发，不再让他按一次发送**：他点这个按钮的时候就已经决定要说这句了。多点一次等于多一个可以放弃的路口，而"最后一个路口"正是这整个软件要拆掉的东西。

**为什么清洗逻辑（`SuggestionCleaner`）要放进 Core**：和 `ReplyCleaner` 一个理由——这条限长、去重、限条数的规则改一点点，用户第一眼就看得见，得让冒烟测试能直接验证，而不是在真实对话里碰运气。模型对"不超过 15 个字、给 2~3 条"这类约束执行得时好时坏，遇到过一次给六条、一次把整句复述塞进来；后端和客户端各拦一道，用的是同一份规则。

### 5.15 同一块日期面板，两个页面共用一份

**起因**：改目标日期最初只写在列表页的「更多」里。后果是想动一天期限，得返回列表、在一排卡片里找到它、再点两层菜单。而人真正会想改日期的时刻，几乎总是**打开详情页看见"还剩 2 天、底下还有 7 条没做"的那一秒**——入口不在眼前，多数人就先不改了，然后到期那天再说"没做完"。

**做法**：抽出 `Controls/DatePickerSheet.xaml`。它只管版式和"把点击转出去"，不管存哪儿：四个命令（确认 / 清空 / 取消 / 快捷日期）由页面注入。

**为什么不干脆复制一份 XAML**：复制当天两份是一样的，漂移从第二天开始——调一次间距、改一句措辞、多加一个快捷按钮，只要漏掉一处，同一个动作在两个页面就长得不一样。这种事不报错、不进日志，只是慢慢让人觉得这软件东一块西一块。而"共用一份"的代价只是一次性把 BindableProperty 样板写出来。

**BindableProperty 是 MAUI 里"能被 XAML 绑定的属性"**：普通 C# 属性绑不上去（框架不知道它什么时候变），写成 `BindableProperty.Create(...)` 之后，读取、写入、"变了通知界面"这三件事由框架负责。代价是每个属性要写一次静态字段 + 一个 `GetValue/SetValue` 包装，看着啰嗦，但这是固定套路。

**一个容易踩的点：控件里的绑定要写 `Source={x:Reference Root}`**。`ContentView` 的 `BindingContext` 是从使用它的页面继承下来的（那里是页面 VM），而面板自己的数据（标题、选中日期）是控件上的 BindableProperty。不写 `Source`，绑定会跑到页面 VM 上找 `SelectedDate`，找不到——而且**不会报错，只是面板永远是空的**。写了之后绑定源固定是控件自己，跟页面 VM 长什么样无关。

**`MinimumDate` 的默认值可以写 `DateTime.Today`**：`BindableProperty.Create` 是普通方法调用而不是 attribute，参数在运行时求值，所以不需要常量。它只在类型初始化时算一次（等于程序启动那天），跨天开着的程序会停在昨天——代价是允许选到昨天，而"选到过去"本来就没禁止，不值得为它加逻辑。

### 5.16 干预引擎：判断放在 Core，出声放在平台

整个功能一句话：**连续刷同一个娱乐应用超过 30 分钟，弹一条不点不走的系统通知。**

**判断为什么是纯函数**（`Core/Intervention/InterventionDecider`）：边界条件有十几种组合——开关、算不算娱乐、到没到阈值、在不在冷却、今天按没按过赦免、还有没有没做完的事。这些错误在实机上极难复现（"昨天它弹了，今天没弹"），只能靠逐条断言。纯函数意味着同样输入永远同样输出，`SmokeTest` 第 20 节把每一支都验了一遍。

**为什么看"这一段连续多久"而不是"今天累计"**：累计是统计，连续是行为。分三次各看 10 分钟，和一口气看 30 分钟，是两种状态。用累计的话，早上看了 25 分钟，晚上一坐下就被提醒——那时人才刚打开，提醒毫无道理。

**为什么必须用 `reminder` 场景**：普通 toast 三五秒就滑走，人还在视频里，眼角扫到一行字就没了，等于没提过。需求里"必须点一下才消失"不是要烦人，是因为**自动消失的提示不产生任何摩擦力**。

**为什么 unpackaged 应用要多写一行 P/Invoke**：本项目不打 MSIX 包（`WindowsPackageType=None`）。没有包身份时系统不知道这个进程是谁，通知发不出去。`SetCurrentProcessExplicitAppUserModelID` 给进程指定一个固定身份，再 `Register()` 注册 COM 激活器，通知才有一条送到屏幕的路。这一步失败只记录、不抛——提醒坏了不能让日程本身跟着起不来。

**为什么名单这么短**：误判的代价不对称。漏掉一个游戏，顶多不被拦，用户自己能标；把 Word 算成娱乐，就会在他干活时弹"你已经用 Word 一小时了"，而那种提醒一次就足够让人关掉整个功能。所以浏览器、微信、音乐播放器一个都不放，全交给用户标。

**为什么赦免要存库、冷却只放内存**：用户按「今天别再提了」是给软件的承诺，重启一次就作废的话这功能不可信；而冷却只是"别太啰嗦"，重启后从头算最多多提一次。同一个功能里两种状态用两种存法，判据是**"失效一次的后果有多严重"**。

**为什么设置页要显示"它现在看到什么"**（`StatusText`）：一个只在该说话时才出声的功能，平时完全静默，用户分不清"还没到 30 分钟""它坏了""它根本没启动"——三种情况在界面上长得一模一样。把这句判断写出来，等于给它一个心跳。

## 六、你迟早会踩的坑

按"踩到的概率 × 排查难度"排序：

1. **编译通过 ≠ 能跑。** EF Core 的查询翻译失败是运行时错误，编译器一声不吭。写完数据库查询一定要真的跑一遍。这也是 `tools/SmokeTest` 存在的原因。

2. **读出来的时间是 UTC。** 显示前 `.ToLocalTime()`，否则差 8 小时。

3. **改了代码没重新编译。** 直接双击 exe 跑的是上一次编译的结果，你会以为改动没生效。用 `start.bat` 或 VS 里按 F5 就不会有这个问题。

4. **用 `List` 当列表数据源。** 数据加了界面没反应。要用 `ObservableCollection`。

5. **颜色写死。** `Colors.Black` 在深色模式下会消失。跟随正文的颜色要按 `RequestedTheme` 取值（见 `ItemViewModel.PrimaryTextColor`）。

6. **忘了 `x:DataType`。** 属性名拼错时界面一片空白且无任何提示。

7. **DbContext 共用一个实例。** 并发报错或内存持续增长。用工厂，每次操作新建。

8. **编译前没关掉正在运行的 App。** 表现是 `MSB3026` / `MSB3027`：`无法将 xxx.dll 复制到 bin\...`，文件被 `DayManager.App (进程号)` 锁定。更麻烦的是重试期间偶尔能复制成功一半——所以改代码之前先确认程序已经关了，别硬编。

9. **`DevicePlatform` 撞名。** MAUI 自己有一个 `Microsoft.Maui.Devices.DevicePlatform`（Android/iOS/WinUI 那套），跟 `Core/Enums.cs` 里的同名。在 App 项目里直接写 `DevicePlatform.Windows` 会得到 `CS0104: 引用不明确`，必须写全 `DayManager.Core.Enums.DevicePlatform.Windows`。

10. **用了字体里没有的符号。** 日程页的翻页按钮曾经用 `‹ ›`（U+2039/U+203A），系统字体里没这两个字形，MAUI 不会像浏览器那样自动找替代字体，于是按钮**静默显示空白**且不报错。界面上的符号只用 ASCII 的 `<` `>` 和已验证的 `✓`。

11. **做小按钮时忘了清 `MinimumHeightRequest`。** 全局 Button 样式设了 `MinimumHeightRequest=44`，它是**下限**，优先级高于 `HeightRequest`：你写 `HeightRequest="28"`，量出来还是 44，且不报错。要小按钮就把下限一起改成 0（见 `ChipButton` 样式）。

12. **`Frame` 从 .NET 9 起过时。** 用 `Border` + `StrokeShape`。编译器会警告，但不会拦你——界面照样跑，只是以后某天会消失。

13. **在统计代码里忘了 `.ToLocalTime()`。** 所有人都记得"界面上显示时间要转本地"，但**仓储里做分组的代码最容易漏**：`GetHourlyAsync` 早期直接取 `.Hour`，结果 11 点的数据全落到凌晨 3 点那根柱子上。凡是"按天/按小时分组"，分组前必须转本地。

14. **COM 接口的 `[Guid]` 凭记忆写。** 表现是 `E_NOINTERFACE`（0x80004002）或 `InvalidCastException`——**和"这台设备的驱动不支持"长得一模一样**，不对照头文件就会往错的方向排查很久。取值一律抄 Windows SDK 头文件（本机在 `C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\um\`）。

    还有个更隐蔽的点：`Activate(IAudioMeterInformation)` 成功之后，把指针转成接口时用的是**接口声明上写的那个 `[Guid]`**，不是传给 `Activate` 的那个。改一处不改另一处，现象是"Activate 成功了但转型失败"，看着特别矛盾。

    排查手段：`dotnet run --project tools/UsageProbe -- --audiodiag` 会用同一个 `Activate` 换几个已知 IID 试一遍——全失败是调用姿势的问题，只有某一个失败才是设备或 IID 的问题。

15. **忘了 SQLite 默认读写互斥。** 默认的 rollback journal 模式下，写的时候不能读、读的时候不能写。本项目正好是"一边每 5 秒写（采集器）、一边读一整天（时间页）"，撞上就是 `SQLite Error 5: database is locked`，而且是偶发的——本地怎么点都好，一挂上自动刷新就天天出现。启动时必须开 WAL（见 `Data/SqliteBootstrap.cs`）。

    顺带两个事实：`journal_mode` 是写在**数据库文件头**里的，设一次永久有效，不用每次连接都设；开了之后目录里会多出 `-wal` 和 `-shm` 两个伴随文件，这是正常的。

16. **新页面自己写一遍卡片样式。** 之前每个页面各写一遍 `Border` 的属性，结果是四个页面的边框色、内边距、圆角各不相同，而且**全都只有描边、没有底色**——卡片和页面完全同色，界面一马平川，看着像没上完的稿子。现在统一走 `{StaticResource CardStyle}`（在 `Resources/Styles/Styles.xaml`），改一处全站生效。

    这条能推广：**凡是"同一种东西出现三次以上"，就要收成样式**。三个地方各写一遍，一定会有某处漏改，而那种不一致说不出哪里怪，但谁都看得出别扭。

17. **聊天列表滚不到底：这里该用 ScrollView，不是 CollectionView。** 对话页最早用的就是 CollectionView，加消息后 `ScrollTo(最后一条)` 总是停在半路——用户得手动划到底才看得见新回复。

    根子在"**什么时候滚**"：气泡的高度要等文字**排完版**才知道，而 AI 一句话能占半屏。高度还未知的时候滚，位置是照旧布局算出来的，于是停在中途；等高度定了，已经没有任何人会再滚一次。CollectionView 只提供"滚到某一条"这一个接口，项有多大它自己管，外面插不上手——补滚几次也救不回来，因为每次的结果都取决于当时的布局。

    换 ScrollView 之后，接口变成**给一个具体位置**：`ScrollToAsync(0, 内容总高)`。这个动作跟排版进行到哪一步无关，什么时候调都是到底，多调几次只是把同一个动作重复一遍，不会越滚越偏。所以后台代码在 30 / 120 / 320 毫秒各滚一次兜底是安全的。

    代价是没有虚拟化：ScrollView 会把列表里每一条都实例化，不像 CollectionView 只渲染看得见的几条。这里的量是可控的（历史一次只加载 50 条，见 `ChatViewModel.LoadLimit`），五十个气泡的开销换一个滚得准的界面，值。

    另外两件事：滚动之间要用 `CancellationTokenSource` 互相取消，否则首次加载几十条历史会攒出几十个滚动任务、上百次滚动，页面会卡一下；内容高度还是 0 时（页面刚出来还没量过）要跳过这一趟，等下一次。

    > 顺带记一个枚举名，将来给别的列表加这个属性时用得上：`ItemsUpdatingScrollMode` 的值是 `KeepLastItemInView`，**不是**很多旧博客里写的 `AlwaysScrollToLastItem`——后者是 Xamarin.Forms 时期的名字，MAUI 里已经没有这个成员，写了直接编译报错 `CS0117`。

18. **把平台相关的代码写进了共享文件。** 比如"按回车就发送"这件事，Windows 要挂 WinUI 的 `PreviewKeyDown`、Android 要监听 `Editor` 的 ImeAction，两边毫无共同点。塞进 `ChatPage.xaml.cs` 只会变成一堆 `#if WINDOWS`，将来加一个平台就要回去改条件，漏一处就编译不过。

    本项目的方式：共享文件里声明 `partial void AttachEnterToSend();`，真正的实现放 `Platforms/Windows/ChatPage.Windows.cs`（类名和命名空间相同，只是多一个文件）。MAUI 编译哪个平台就带上哪个目录，其他平台根本看不到 WinUI 的类型。

    `partial` 方法在这里还有个额外好处：**没有实现时，调用会被编译器直接删掉**。所以接 Android 时即使暂时没写实现，也不会编译失败，只是回车还不响应——比一堆 `#if` 少一个出错的机会。

    顺带一个必踩的坑：原生控件是**延迟创建**的。页面构造函数里 `Editor.Handler?.PlatformView` 通常还是 `null`，要同时订阅 `HandlerChanged` 事件，等它建好再挂；而且挂之前要判断"已经挂过没有"，否则 Handler 重建一次就重挂一次，表现是按一下回车发出两条消息。

19. **后端由客户端拉起时，控制台日志等于没有。** `BackendLauncher` 用隐藏窗口启动后端，输出不重定向——`ILogger` 写的所有东西随窗口一起消失。平时开发用 `start.bat` 能看见，等真出事的那天（比如用户双击 exe 直接开）就什么都查不到。2026-10-27 的教训：AI 连续三次空回复，事后想查，诊断日志早已烟消云散。**关键诊断必须落文件**（`logs/api-ai.log`，见 `Services/AiDiagnostics.cs`），控制台那份只算给开发时的赠品。

20. **显示属性只在部分分支里赋值。** `ItemViewModel.Refresh()` 曾经只在"完成"和"不做了"两个分支里给 `TitleDecorations` 赋值，其余分支一个字都不碰。后果是一出具体的画面：勾上完成 → 标题划掉；再点一下取消勾选 → **删除线还在**（颜色倒是变回来了，因为 `TitleColor` 每个分支都设了）。更烦人的是从「更多」菜单里改状态看不出这个毛病——那条路会整页重查、重新 new 一个 ViewModel，属性回到默认值；**同一个 bug，换个入口就藏起来了**，于是报障听起来像"时灵时不灵"。规矩：凡是"只有少数状态才显示"的属性（删除线、徽章、提示红点），在 `Refresh()` 开头一律先清到默认值，再按需设，不要指望别的分支替你清。

## 七、动手练习（从易到难）

改代码是唯一能把知识变成自己的方式。每做完一个，重新编译跑一遍看效果。

1. **改一个显示文案**：在 `ItemViewModel.cs` 里把"待办"改成"还没开始"，看界面变化。
2. **加一个字段的显示**：让副标题里显示优先级（高/中/低）。提示：`_item.Priority` 已经在数据里了。
3. **改状态颜色**：把"进行中"的圆圈颜色从 `DarkOrange` 改成别的。
4. **加一个排序**：在 `ItemRepository.GetTodayListAsync` 里让"进行中"的条目排在最前面。
5. **加一个新命令**：在 `MainViewModel` 里加一个"全部标记为完成"的命令，并在 `MainPage.xaml` 里加个按钮绑上去。
6. **加一个新字段（完整走一遍）**：给 `Item` 加一个"地点"字段 → 生成迁移 → 在 Repository 的新建方法里赋值 → 在界面上显示。这一条会让你把整条链走通。
7. **给时间页加一个统计口径**：在 `TimeViewModel` 里算"平均每条会话多长"，显示在摘要卡片里。提示：数据都在 `UsageRange` 里，不用动数据库。
8. **改采集粒度**：把 `WindowsUsageTracker.SampleInterval` 从 5 秒改成 2 秒，观察一天下来会话条数怎么变。想清楚"更细"换来的代价是什么。

跑验证程序：

```bash
# 164 项断言，覆盖清单过滤、五态流转、软删除、大任务进度、撤销、对话持久化、
# AI 回复清洗、使用时长统计
dotnet run --project tools/SmokeTest

# 不开界面验证采集器（采 20 秒后把刚落的会话打出来）
dotnet run --project tools/UsageProbe -- --simulate 20

# 只读音频电平：静音读几次 -> 播一段系统声音 -> 停止再读，看 0 -> 非 0 -> 0
dotnet run --project tools/UsageProbe -- --audio 9 --playtest
```

**为什么要有这两个程序**：EF Core 的查询翻译失败、时间时区错位、状态口径不一致，这些**编译期全都发现不了**，只能真跑一遍看数字。改了数据层之后跑一遍，能立刻发现逻辑有没有坏。

## 八、术语速查

| 名词 | 一句话 |
|---|---|
| .NET SDK | C# 的编译器 + 类库 + 命令行工具，合起来一套 |
| workload | 装在 SDK 之上的平台支持包（我们装了 android 和 windows） |
| NuGet | .NET 的第三方库仓库，类似 pip |
| csproj / slnx | 项目文件 / 解决方案文件（后者是 .NET 10 的新格式，登记有哪些子项目） |
| TargetFramework | 这份代码编译到哪个平台 |
| 依赖注入（DI） | 不在代码里 new，由框架统一创建并送过来 |
| DbContext | EF Core 的数据库会话对象 |
| 迁移（Migration） | 把数据库从旧结构改成新结构的脚本 |
| Fluent API | 用链式方法（而不是注解）配置表结构 |
| 值转换器 | 入库前把 C# 类型转成数据库能存的类型 |
| 软删除 / 墓碑 | 不真删，只标记删除时间，让"删除"能被同步出去 |
| MVVM | Model / View / ViewModel 三层分工 |
| 数据绑定 | 界面控件直接绑到数据属性，数据变界面自动变 |
| INotifyPropertyChanged | "属性变了"的通知机制，数据绑定的基础 |
| XAML | 用 XML 描述界面结构，会编译成真正的代码 |
| partial | 一个类的定义可以分散在多处（含工具生成的那部分） |
| Attribute（特性） | 贴在代码上的元数据，被工具在编译期读取 |
| 源生成器 | 编译时自动帮你写代码的工具（MVVM 工具包用的就是它） |
| lambda | `x => ...`，读成"对于每个 x" |
| LINQ | 用 C# 语法写查询，EF Core 会把它翻译成 SQL |

## 九、下一步

**当前进度**：Windows 端四个界面都通了（对话 / 日程 / 大任务 / 时间），数据层、后端 AI、使用时长采集都在跑。接下来两件事：

1. **M9 干预引擎**：拿真实的 `usage_sessions` 数据判断"该不该提醒"。这块要碰的是：
   - 阈值怎么定（用时长超过 X 分钟 / 连续专注 Y 小时）
   - 提醒怎么呈现（点一下才消失的摩擦，而不是弹窗阻断）
   - "今天别再提了"的赦免权——没有它，这软件会变成骚扰工具被关掉
2. **M10 Android**：数据模型和接口已经预留好了，缺的是 `UsageStatsManager` 那份采集实现（只能拿到包名，拿不到窗口标题），以及本地闹钟提醒。

再往后才是服务端推送、用户画像、AI 自动排时段。**顺序不能反**：自动排时段的依据是真实的 `actual_minutes`，先有真实数据才谈得上校准。

现在打下的这几层（实体 → 数据层 → 界面）到时候都能直接复用。
