## 一、先建立地图

### 1.1 四个项目各自负责什么

```
DayManager.Core   ── 定义"数据长什么样"（零框架依赖）
      ↑
DayManager.Data   ── 定义"数据怎么存进 SQLite"
      ↑
   ┌──┴───────────────┐
DayManager.App      DayManager.Api
（手机 + 电脑界面）   （服务端，目前几乎是空的）
```

箭头方向是"引用"：`Data` 引用 `Core`，`App` 引用 `Data`。**引用是单向的**——`Core` 不知道 `Data` 的存在，这就是"分层"。

**为什么 `Core` 要单独一层、而且不引用任何框架？**

因为手机端、电脑端、服务端三方都要用同一份"一条日程包含哪些字段"的定义。如果各写一份，迟早出现"电脑上加了字段，手机上没有"——这类 bug 极难查。共用一份定义，从根上消灭它。

保持零依赖的代价是：不能用 `[Table("items")]` 这种 EF Core 的注解（那会逼着 `Core` 引用 EF Core），所以表结构的配置改在 `Data` 层用代码写（这就是后面讲的 Fluent API）。

### 1.2 一次"打勾完成"的完整旅程

理解这条链，整个程序就通了：

```
① 你在界面上点圆圈
        ↓
② MainPage.xaml 里写着 Command="{Binding ToggleCompleteCommand}"
        ↓
③ 这一行让 MAUI 去调 MainViewModel 里的 ToggleCompleteAsync 方法
        ↓
④ ViewModel 调 _itemRepository.SetStatusAsync(id, Done)
        ↓
⑤ Repository 通过 DbContext 改数据库里的那一行
        ↓
⑥ 数据库返回新的 Item，ViewModel 更新界面的显示属性
        ↓
⑦ 界面自动刷新（因为属性变了会发出通知）
```

每一层只跟相邻的一层说话，这就是分层的好处：改数据库不用动界面，改界面不用动数据库。

## 二、C# 语言基础（全部用本项目代码举例）

### 2.1 命名空间与 using

```csharp
namespace DayManager.Core.Entities;   // 声明"我属于这个命名空间"

using DayManager.Core.Enums;          // 引入别的命名空间，之后才能直接用里面的类型
```

分号结尾的写法（不是大括号）是较新的"文件级命名空间"，整个文件都属于它，省一层缩进。

命名空间可以理解为"姓氏"：`Item` 的全名是 `DayManager.Core.Entities.Item`。不写 `using` 就得写全名，太啰嗦。

### 2.2 类、属性、自动属性

打开 `Item.cs`，你会看到大量这种写法：

```csharp
public string Title { get; set; } = string.Empty;
public bool IsAllDay { get; set; }
public int? DurationMinutes { get; set; }
```

这叫**自动属性**（auto-property）。它一行顶三件事：

- `Title` 是对外暴露的属性名
- `get; set;` 表示可读可写
- 背后那个存值的字段由编译器自动生成，你不用写

为什么 C# 要这么设计，而不像 C++ 那样直接暴露成员变量？因为属性可以在将来加上逻辑（比如赋值时校验），而**调用方的写法完全不用变**。`item.Title = "x"` 这行代码，不管 `Title` 是简单字段还是复杂属性，长得一模一样。这是"为未来留后路"的经典手法。

`= string.Empty` 是初始值。给字符串一个空串而不是让它为 null，可以避免后面到处写判空。

### 2.3 可空类型 —— C# 里最容易误解的一处

项目里到处是 `?`，但**值类型和引用类型的 `?` 含义不同**：

```csharp
public DateTimeOffset? StartAt { get; set; }   // 值类型 + ? = "可能没有值"
public string? Notes { get; set; }             // 引用类型 + ? = "编译器请你提醒我它可能为 null"
```

- `DateTimeOffset` 是**值类型**（struct），本身永远有值（默认 0001 年），加 `?` 之后才允许"没有值"。数据库里对应"该列可以为 NULL"。
- `string` 本来就可以是 null。加 `?` 主要是给编译器的一个**声明**：我知道它可能为空，如果我忘了判空就警告我。

这套机制的目的很实际：**把"空引用崩溃"从运行时提前到编译期**。当你看到 `x.StartAt?.ToLocalTime()` 这种写法，那个 `?.` 就是"如果为空就整条表达式返回空，不往下走"——一行代码代替了三行 if。

相关运算符，项目里全都用到了：

| 写法 | 含义 | 项目里的例子 |
|---|---|---|
| `?.` | 为空就短路，不继续 | `_item.StartAt?.ToLocalTime()` |
| `??` | 左边为空就用右边 | `x.StartAt ?? x.DueAt ?? x.CreatedAt` |
| `??=` | 只在为空时才赋值 | `item.StartedAt ??= now;` |
| `is null` | 判空（比 `== null` 更可靠） | `if (item is null) return null;` |

`??=` 那一行特别值得记住，它在 `ItemRepository.SetStatusAsync` 里：

```csharp
item.StartedAt ??= now;
```

意思是"只在 StartedAt 还是空的时候写入当前时间"。如果用普通的 `=`，你手滑点两次"开始"，首次开始时间就被刷掉了——而这是算"启动延迟"的核心数据，**错了还没任何提示**。

### 2.4 枚举

`Enums.cs`：

```csharp
public enum ItemStatus
{
    Pending = 0,
    InProgress = 1,
    Done = 2,
    Cancelled = 3
}
```

枚举就是把"一组固定的取值"起上名字。数据库里存的是整数 0/1/2/3，代码里写的是 `ItemStatus.Done`。

**为什么显式写出 `= 0` `= 1`？** 因为不写的话编译器也会从 0 开始自动编号，但一旦将来有人在中间插入一个新状态，后面所有数字都会顺移——而数据库里已经存了旧数字，于是全部错位。显式写死是防止这种"改一行代码导致历史数据全错"的保险。

### 2.5 继承

```csharp
public abstract class SyncEntityBase   // 基类
{
    public Guid Id { get; set; }
    public int Version { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public DateTimeOffset UpdatedAt { get; set; }
    public DateTimeOffset? DeletedAt { get; set; }
}

public class Item : SyncEntityBase     // Item 继承它，自动拥有上面全部字段
{
    public string Title { get; set; } = string.Empty;
    // ...
}
```

`abstract` 表示"这个类只是个模板，不能直接 new"。

为什么要把同步相关的字段抽成基类？因为**以后新增的任何表都不该漏掉同步能力**。放在基类里，新建实体时 `: SyncEntityBase` 一写，这些字段自动就有了，不可能忘。

这也是"不要重复自己"原则的一个应用：规则只写一处。

### 2.6 表达式体成员 `=>`

```csharp
public DbSet<Item> Items => Set<Item>();
public Guid Id => _item.Id;
private static Color PrimaryTextColor =>
    Application.Current?.RequestedTheme == AppTheme.Dark ? Colors.White : Colors.Black;
```

`=>` 在这里表示"这个属性的值就是右边这个表达式"，等价于 `{ return ...; }`，只是短。

注意它和 lambda 表达式（下面会讲）用的是同一个符号，但在属性定义的位置上含义是"简写的 get"。

### 2.7 字符串插值

```csharp
parts.Add($"完成于 {completedLocal.Value:HH:mm}");
parts.Add($"逾期 {today.DayNumber - dueDay.DayNumber} 天");
```

`$` 开头的字符串里，`{...}` 内可以写任意表达式。冒号后面是格式（`HH:mm` 表示只显示时分）。

比 `"完成于 " + x.ToString("HH:mm")` 可读性好太多，这是 C# 里用得最多的语法糖之一。

### 2.8 集合与 LINQ

`ItemRepository.GetTodayListAsync` 里密集出现：

```csharp
var scheduledToday = db.Items.Where(x =>
    x.StartAt >= dayStart
    && x.StartAt < dayEnd
    && x.Status != ItemStatus.Cancelled);

return items
    .OrderBy(x => x.StartAt != null ? 0 : x.DueAt != null ? 1 : 2)
    .ThenBy(x => x.StartAt ?? x.DueAt ?? x.CreatedAt)
    .ThenBy(x => x.SortOrder)
    .ToList();
```

**LINQ**（Language Integrated Query）是一套用 C# 语法写"查询"的机制。`Where` 是筛选，`OrderBy`/`ThenBy` 是排序，`ToList()` 是执行并取出结果。

`x => ...` 这个叫 **lambda 表达式**，读成"对于每一个 x，做……"。`x` 的类型由编译器推断，不用写。

⚠️ **本项目最关键的一个坑就在这里**：`db.Items.Where(...)` 并不会在 C# 里执行，EF Core 会把整个表达式**翻译成 SQL 发给数据库**。所以不是所有 C# 写法都能用——翻译不了的就在运行时抛异常。详见第六节。

另一个重要区别：

```csharp
public ObservableCollection<ItemViewModel> TodayItems { get; } = new();
```

`ObservableCollection` 会在内容变化时**自动通知界面刷新**。换成 `List` 的话，你 `Add` 完界面纹丝不动——这是新手最常卡住的地方："数据明明加了，怎么界面没反应"。

`new()` 是"目标类型 new 表达式"，简写了 `new ObservableCollection<ItemViewModel>()`。

### 2.9 async / await

`ItemRepository` 里每个方法都是这样：

```csharp
public async Task<List<Item>> GetTodayListAsync(DateOnly? day = null, CancellationToken ct = default)
{
    await using var db = await _dbFactory.CreateDbContextAsync(ct);
    var items = await query.ToListAsync(ct);
    return items;
}
```

三个关键字：

- `async`：标记"这个方法里有等待"。
- `await`：**等待一个耗时操作完成，但不卡住界面**。执行到这里，方法会把控制权交还给调用方（界面继续能响应），等数据库返回后再接着往下走。
- 返回类型 `Task<T>`：表示"将来会给你一个 T"。`Task`（不带泛型）表示"将来会完成，但不返回值"。

为什么要有这套东西？因为访问数据库、网络请求这些操作可能要几百毫秒。如果同步等待，界面会整个冻住。对手机应用来说这是致命的。

`CancellationToken ct = default` 是"允许调用方中途取消"，好习惯，虽然现在还没用到。

`await using` 是 `using` 的异步版，表示"用完自动释放"（这里释放的是数据库连接）。

**`await` 会传染**：一个方法里用了 `await`，它自己就得标 `async`；调用它的方法也得 `await`……一路传到最上层。你会看到 `MainViewModel` 里所有命令方法都带 `async Task`，根因就在这。

### 2.10 partial（部分类 / 部分属性）

```csharp
public partial class ItemViewModel : ObservableObject
{
    [ObservableProperty]
    public partial string Title { get; set; } = string.Empty;
}
```

`partial` 意思是"这个类的定义可以分散在多个文件里，编译器会拼起来"。

这里有个更妙的用法：`[ObservableProperty]` 这个特性会让 CommunityToolkit 在**编译时自动生成** `Title` 属性的另一半实现——包括"值变化时发出通知"的逻辑。你只写声明，样板代码由工具补。

所以看到 `partial` 就要意识到：**这个东西的另一半不在你眼前，是工具生成的**。

（顺带说：老教程里常见的是 `private string title;` 加 `[ObservableProperty]`，让工具生成 `Title`。那种写法在 WinUI/AOT 下会报警告，现在推荐上面这种 partial 属性写法。）

### 2.11 特性（Attribute）

```csharp
[ObservableProperty]
public partial string Title { get; set; } = string.Empty;

[RelayCommand]
private async Task LoadAsync() { ... }
```

方括号里的叫**特性**，它给代码元素贴上元数据。本身不执行任何逻辑，而是被别的工具在编译期或运行期读取。

`[RelayCommand]` 会自动生成一个叫 `LoadCommand` 的属性（方法名去掉 `Async` 加 `Command`），于是 XAML 里可以写 `Command="{Binding LoadCommand}"`。手写这个本来要二三十行。

这类"用特性驱动代码生成"的做法在现代 C# 里非常普遍，它把重复劳动从你的指尖移到了编译器。

### 2.12 泛型

```csharp
public DbSet<Item> Items => Set<Item>();
private readonly IDbContextFactory<AppDbContext> _dbFactory;
public async Task<Item?> SetStatusAsync(...)
```

`<T>` 里的 T 是"类型参数"。`DbSet<Item>` 读作"装 Item 的 DbSet"。

好处是**一份代码适配多种类型，还保证类型安全**：`List<Item>` 里只能放 `Item`，放错编译就报错。对比一下没泛型时代的 `ArrayList`（什么都能放，取出来要手动强转，容易崩）。

`Task<Item?>` 读作"将来给你一个可能为 null 的 Item"。

### 2.13 接口

```csharp
private readonly IDbContextFactory<AppDbContext> _dbFactory;
```

`I` 开头是 .NET 的命名惯例，表示接口。接口只定义"能做什么"，不定义"怎么做"。

这里的好处是：字段声明成接口类型，以后换一种实现（比如换成内存数据库做测试）**不用改任何调用它的代码**。这就是"面向接口编程"。

### 2.14 异常与 try/catch/finally

`MainViewModel.LoadAsync` 里：

```csharp
IsBusy = true;
try
{
    var items = await _itemRepository.GetTodayListAsync();
    // ...
}
catch (Exception ex)
{
    await ReportErrorAsync(ex);
}
finally
{
    IsBusy = false;
}
```

- `try`：可能出错的代码
- `catch`：出错时怎么办
- `finally`：**不管出没出错都会执行**——所以 `IsBusy = false` 放这里，保证不会永远卡在加载中

`await using var db = ...` 和 `using var scope = ...` 也是同一类思路：确保资源一定被释放，哪怕中途抛异常。

### 2.15 static readonly

```csharp
private static readonly ValueConverter<DateTimeOffset, long> DateTimeOffsetToLong = new(...);
```

- `static`：属于类，不属于某个实例，全局一份
- `readonly`：只能在初始化时赋值，之后不能改

合起来就是"一个全局共享、且不会被意外改掉的常量对象"。这里用它是因为转换器是无状态的，没必要每次 new 一个。

## 三、.NET 与 MAUI 生态概念

### 3.1 项目文件与目标框架

`DayManager.App.csproj` 里：

```xml
<TargetFrameworks>net10.0-android</TargetFrameworks>
<TargetFrameworks Condition="$([MSBuild]::IsOSPlatform('windows'))">
    $(TargetFrameworks);net10.0-windows10.0.19041.0
</TargetFrameworks>
```

`TargetFramework`（目标框架）决定"这份代码编译到哪个平台"。一份源码编出两个平台的产物，这是 MAUI 的核心价值。

`net10.0-windows10.0.19041.0` 里那串数字是 Windows SDK 的版本号，不是随便写的。

### 3.2 NuGet 包

`dotnet add package Microsoft.EntityFrameworkCore.Sqlite` 做的事就是：从 NuGet（.NET 的包仓库，类似 Python 的 pip）下载库，并在 `.csproj` 里记一笔。

`.csproj` 是 XML，可以直接打开看，里面就是"我引用了哪些包、编到哪些平台"。

### 3.3 依赖注入（DI）

`MauiProgram.cs` 是启动时的一张"装配清单"：

```csharp
builder.Services.AddDbContextFactory<AppDbContext>(options =>
    options.UseSqlite($"Data Source={dbPath}"));

builder.Services.AddSingleton<ItemRepository>();
builder.Services.AddTransient<MainViewModel>();
builder.Services.AddTransient<MainPage>();
```

意思是"登记：谁需要东西，就从我这儿拿"。于是 `ItemRepository` 的构造函数里写个参数就能拿到数据库工厂：

```csharp
public ItemRepository(IDbContextFactory<AppDbContext> dbFactory)
{
    _dbFactory = dbFactory;
}
```

你从来没有写过 `new ItemRepository(...)`——是框架创建的。

**三种生命周期**（这是面试常问，也是实际会踩坑的地方）：

| 生命周期 | 含义 | 本项目例子 |
|---|---|---|
| Singleton | 整个程序共用一个实例 | `ItemRepository`（不持有业务状态，共用没问题） |
| Transient | 每次要都新建一个 | `MainViewModel`（持有"今天的清单"等状态，每次打开页面都该是干净的） |
| Scoped | 一个作用域内共用一个 | Web 里通常是一次请求 |

为什么 `MainViewModel` 不能用 Singleton？因为它存着"当前清单、输入框内容"。共用的话，第二次打开页面会带着上一次的旧数据。

### 3.4 为什么用 `IDbContextFactory` 而不是直接注入 `DbContext`

```csharp
await using var db = await _dbFactory.CreateDbContextAsync(ct);
```

`DbContext` 有两个特点：**不是线程安全的**（两处代码同时用会报错），而且**会缓存查过的数据**（长期共用一个实例，内存越滚越大）。

所以正确用法是"每次操作现开一个短命实例，用完即弃"。工厂就是干这个的。后面做后台采集线程时，这一点会变得非常关键。

### 3.5 EF Core：把 C# 对象变成数据库记录

| 概念 | 是什么 | 本项目对应 |
|---|---|---|
| `DbContext` | 一次数据库会话 | `AppDbContext` |
| `DbSet<T>` | 一张表 | `Items`、`Projects` |
| Fluent API | 用代码配置表结构 | `ConfigureItem(...)` 里那一串 `b.Property(...)` |
| 迁移（Migration） | 建表/改表的脚本 | `Migrations/` 目录 |
| 导航属性 | 表之间的关系 | `Item.Project` |

**迁移是必须理解的概念**：你改了 C# 类，数据库不会自己跟着变。迁移就是"把数据库从旧结构改成新结构"的脚本，有了它才能安全升级已有的数据库，而不是删库重来。

生成迁移的命令：

```bash
dotnet ef migrations add 名字 --project src/DayManager.Data --context DayManager.Data.AppDbContext
```

**`Migrations/` 里的文件是自动生成的，不要手改。** 要改表结构就改实体类，然后生成新迁移。

### 3.6 MVVM 与数据绑定

```
Model      = Item             数据，不知道界面的存在
View       = MainPage.xaml    界面，不含业务逻辑
ViewModel  = ItemViewModel    把数据翻译成界面能直接显示的样子
```

为什么不让界面直接绑定 `Item`？因为界面要的东西和数据库存的东西经常不是一个东西：

- 数据库里 `Status = 2`（整数）→ 界面上要显示"完成"和灰色
- 数据库里三个可能为空的时间字段 → 界面上要显示成一句话"逾期 3 天"

把这些格式化代码写进 XAML，XAML 会没法读；写进 `Item`，Core 层就被界面细节污染了。所以中间加一层专门做翻译，这就是 VM 的本职工作。

**数据绑定**的核心机制是 `INotifyPropertyChanged`：属性变化时发出一个"我变了"的通知，绑了它的控件自动刷新。你不需要写 `label.Text = xxx`。

`[ObservableProperty]` 就是让工具帮你实现这套通知，一个属性省十几行样板代码。

### 3.7 XAML 是什么

`MainPage.xaml`：

```xml
<Label Text="{Binding DateText}" FontSize="13" TextColor="Gray" />

<CollectionView ItemsSource="{Binding TodayItems}" SelectionMode="None">
```

XAML 本质是一棵**对象树**：`<Label .../>` 这一行等价于后台代码里的 `new Label { Text = "..." }`。

`{Binding xxx}` 读作"去 BindingContext 里找 xxx 这个属性"。`BindingContext` 在 `MainPage.xaml.cs` 里被设成了 `MainViewModel`，所以 `{Binding DateText}` 就是 ViewModel 里那个属性。

**`x:DataType` 一定要写**：

```xml
x:DataType="vm:MainViewModel"
```

加上它之后，如果你把属性名拼错（比如写成 `SummaryTxt`），**编译期就报错**；不写的话，要等到运行时才发现界面一片空白，而且没有任何提示。

## 四、逐个文件的精读路线

按这个顺序读，每读完一站你应该能回答后面的问题。

### 第 1 站 · Core：数据在说什么

| 顺序 | 文件 | 行数 | 看什么 |
|---|---|---|---|
| 1 | `Core/Entities/SyncEntityBase.cs` | 80 | 同步三件套（version / 时间戳 / 软删除） |
| 2 | `Core/Entities/Item.cs` | 194 | 一条日程的完整字段 |
| 3 | `Core/Enums.cs` | 106 | 状态、优先级、日期类型 |

**读完自测**：用自己的话说出"一条日程包含哪些信息"，以及"为什么 DeletedAt 存在而不是直接删掉"。

**重点理解**：

- `Id` 用 `Guid` 而不是自增数字 —— 手机离线时也要能创建记录，那时拿不到服务端分配的自增 ID，而自己编数字一定会和电脑撞车
- `Version` 用于冲突检测，且不依赖两台设备的时钟一致
- `StartedAt` + `CreatedAt` = 你的"启动延迟"指标，这是整个项目最有个人价值的两个字段
- `RecurrenceParentId` 不叫 `ParentId` —— 因为项目层级也有父子（`ParentTaskId`），两个语义混在一起会写出极难查的 bug

### 第 2 站 · Data：怎么落盘

| 顺序 | 文件 | 行数 | 看什么 |
|---|---|---|---|
| 4 | `Data/AppDbContext.cs` | 306 | 表结构、值转换器、软删除过滤、SaveChanges 重写 |
| 5 | `Data/Repositories/ItemRepository.cs` | 267 | 今日清单的判定、状态流转 |

**读完自测**：为什么"逾期未完成"的待办会自动出现在今天？

`AppDbContext` 里三处必看：

1. **值转换器**（第 93–144 行）：把时间统一转成 Unix 毫秒整数存。原因见第六节。
2. **全局查询过滤**（第 195 行）：`b.HasQueryFilter(x => x.DeletedAt == null)` —— 普通查询自动看不到已删记录，但做同步时必须用 `IgnoreQueryFilters()` 把墓碑查出来。
3. **重写 SaveChanges**（第 256–305 行）：`Version++` 和 `UpdatedAt` 在这里统一处理。**为什么不在业务代码里写？** 因为只要有一处忘记，同步时就会误判"这条没改过"，而且这种错误是静默的。集中在一处，所有路径都逃不掉。

### 第 3 站 · App：怎么变成能点的界面

| 顺序 | 文件 | 行数 | 看什么 |

## 五、本项目里"反直觉"的几个决定

这些是光看代码想不通、必须知道背景的。

### 5.1 时间全部存成整数

数据库里打开看，`StartAt` 是一串数字而不是日期。因为 EF Core 的 SQLite 提供程序**不支持比较 DateTimeOffset**——`Where(x => x.StartAt >= 今天零点)` 这种查询编译没问题，运行时直接抛异常。

改成存 Unix 毫秒后：整数能直接比大小，而且表示绝对时刻，顺带解决了跨时区比较的隐患。

**代价**：读出来的时间是 UTC，显示前必须 `.ToLocalTime()`。漏掉就会得到"看着对但差 8 小时"的结果，非常难查。`ItemViewModel.BuildSubtitle()` 里专门为此写了注释。

### 5.2 删除不是真的删除

`SoftDeleteAsync` 只把 `DeletedAt` 填上时间。因为真删掉的话，另一台设备同步时不知道"这条被删了"，会当成从来没存在过，于是又同步回来。

### 5.3 逾期任务自动滚到今天

`GetTodayListAsync` 里的第二类条件。理由很实在：**如果逾期的东西不自动滚过来，软件就等于帮你把它遗忘了**——恰好放大你说的"想着等下再做然后就拖掉"。而且界面上会显示"逾期 3 天"，让它赖不掉。

### 5.4 `StartedAt` 只写一次

`item.StartedAt ??= now;` —— 防止手滑点两次就刷新掉首次开始时间，那会让"启动延迟"数据静默失真且不可逆。

### 5.5 数据库位置写死在代码里

`MauiProgram.cs` 里：

```csharp
var dataDir = OperatingSystem.IsWindows()
    ? @"F:\DayManager\data"
    : FileSystem.AppDataDirectory;
```

之前用过环境变量 `DAYMANAGER_DATA_DIR`，后来删了。因为那制造了两个来源：从 bat 启动（有变量）和直接点 exe（没变量）会落到两个不同的库，表现为"清单突然空了"。

**教训：这类基础配置，单一来源比灵活重要得多。**

Android 上不能写死路径（没有盘符，且往任意目录写会被系统拒绝），所以必须走 `FileSystem.AppDataDirectory`。

## 六、你迟早会踩的坑

按"踩到的概率 × 排查难度"排序：

1. **编译通过 ≠ 能跑。** EF Core 的查询翻译失败是运行时错误，编译器一声不吭。写完数据库查询一定要真的跑一遍。这也是 `tools/SmokeTest` 存在的原因。

2. **读出来的时间是 UTC。** 显示前 `.ToLocalTime()`，否则差 8 小时。

3. **改了代码没重新编译。** 直接双击 exe 跑的是上一次编译的结果，你会以为改动没生效。用 `start.bat` 或 VS 里按 F5 就不会有这个问题。

4. **用 `List` 当列表数据源。** 数据加了界面没反应。要用 `ObservableCollection`。

5. **颜色写死。** `Colors.Black` 在深色模式下会消失。跟随正文的颜色要按 `RequestedTheme` 取值（见 `ItemViewModel.PrimaryTextColor`）。

6. **忘了 `x:DataType`。** 属性名拼错时界面一片空白且无任何提示。

7. **DbContext 共用一个实例。** 并发报错或内存持续增长。用工厂，每次操作新建。

## 七、动手练习（从易到难）

改代码是唯一能把知识变成自己的方式。每做完一个，重新编译跑一遍看效果。

1. **改一个显示文案**：在 `ItemViewModel.cs` 里把"待办"改成"还没开始"，看界面变化。
2. **加一个字段的显示**：让副标题里显示优先级（高/中/低）。提示：`_item.Priority` 已经在数据里了。
3. **改状态颜色**：把"进行中"的圆圈颜色从 `DarkOrange` 改成别的。
4. **加一个排序**：在 `ItemRepository.GetTodayListAsync` 里让"进行中"的条目排在最前面。
5. **加一个新命令**：在 `MainViewModel` 里加一个"全部标记为完成"的命令，并在 `MainPage.xaml` 里加个按钮绑上去。
6. **加一个新字段（完整走一遍）**：给 `Item` 加一个"地点"字段 → 生成迁移 → 在 Repository 的新建方法里赋值 → 在界面上显示。这一条会让你把整条链走通。

跑验证程序：

```bash
dotnet run --project tools/SmokeTest
```

16 项断言，覆盖今日清单过滤、状态流转、软删除、时间往返一致。改了数据层之后跑一遍，能立刻发现逻辑有没有坏。

## 八、术语速查

| 名词 | 一句话 |
|---|---|
| .NET SDK | C# 的编译器 + 类库 + 命令行工具，合起来一套 |

| TargetFramework | 这份代码编译到哪个平台 |
| 依赖注入（DI） | 不在代码里 new，由框架统一创建并送过来 |
| DbContext | EF Core 的数据库会话对象 |

| 数据绑定 | 界面控件直接绑到数据属性，数据变界面自动变 |
