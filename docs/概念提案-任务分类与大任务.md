## 一、先说清楚：我改了立场

三根轴是我 11-21 提出、11-22 落地、并亲手写进《项目全景》《阅读指南》和长期笔记的。  
**现在我主张收掉它。** 推翻它的不是新想法，是两样我自己的东西：真实数据，和我自己写的代码。

当初推它的理由——「分类要能自由组合，将来加一个维度不用回头改类型清单」——在抽象层面并不错。  
错的是**做法**：先按「这几个问题在逻辑上能不能各自回答」搭好骨架，再等数据来填格。  
而这是一个自用、单用户、两周就长完全部数据的软件。骨架搭完，数据没长进去。

这跟用户先后说过的「越做越冗余」「越来越看不懂」「UI 有一点繁杂」是同一个毛病的第 N 次发作，  
只是这次发作在数据结构里，界面上看不见，所以更晚才被发现。

## 二、证据

### 2.1 真实库长什么样（2026-11-22 只读查询，180 条记录）

| 组合（落哪天 / 怎么算完成 / 判成败） | 条数      | 说明                     |
| --------------------- | ------- | ---------------------- |
| 定日 / 做一次 / 判          | **165** | 两周真实数据，全是这一格           |
| 定点 / 做一次 / 判          | 12      | 有钟点的日程，历史回填            |
| 定段 / 做一次 / 判          | 2       | 11-22 刚给「只有截止日」界面入口后建的 |
| 定日 / 每次各算 / 判         | 1       | 11-22 刚给「每天」界面入口后建的    |

其余取值全部为 **0**：`Shape=3`（无锚）0 条、`CompletionMode=ByChildren`（容器）0 条、  
`ParentTaskId` 非空 0 条、`VerdictMode=Never`（一直不判）0 条。

要紧的一句：真正跑过两周的只有**一格**；另外 3 种是给入口当天才造出来的，只算「刚能建」，  
不算「验证过」。而且 165 条同格说明：种类少有一半原因是之前根本没有入口，不是现实里没这种事。

### 2.2 把三根轴交叉的 12 个格子逐格试填

按 ①落哪天 × ③怎么算完成 切（②「是不是容器」落在第三列），结果：

- **4 格真有例子且有数据**：今天写作业 / 周一 10 点开会 / 12-15 交报告 / 每天背单词。
- **5 格说得通、但库里空着**：数学竞赛（带截止日的容器）/ 每天 7 点起床 / 12-15 交的备赛大任务 /  
  随手记下的想法 / 没截止日的大目标。其中「每天 7 点起床」是用户 11-21 明确举过的闹钟类需求，  
  只是 `RRule` 展开没做，建不出来。
- **3 格填不出**：定点容器（每周例会挂议程，硬凑）、定段 × 每次各算（一个截止日却要多次结算，  
  自相矛盾）、无锚 × 每次各算（没有时间锚点却要求「每次」）。

**最后 3 格不是「暂时没遇到」，是这套坐标系自己画出来的无效象限。**  
所以我上一轮说「一半复杂度是给没落地的能力预留的」并不准确，得更正为：  
它不是超前预留，是**既超前又不严谨**——给没发生的事留了位置，留的位置里还混了重复计数和无效象限。

### 2.3 更硬的一条：名义三根轴，实现里不是三根独立维度

- ②「是不是容器」和③「按子项汇总」在实现里是**同一个字段** `CompletionMode.ByChildren`：  
  `AddContainerAsync` 创建容器写的就是它（`ItemRepository.cs:445`）；  
  `ItemAxes.EntersDayList` 判断「这是容器、别进清单」读的也是它（`ItemAxes.cs:80`）；  
  `ItemTools.cs:191` 的注释直接写「容器（ByChildren）」。  
  也就是说，表格第三列那些填不出的格子，根源是②压根不是一根独立的轴，  
  它是③某个取值的另一种说法。
- 更要命的是，「是不是容器」在代码里还有**第二个答案**：  
  `ItemAxes.IsContainer(bool hasChildren)`（`ItemAxes.cs:87`）判的是「有没有子项」。  
  同一个问题，一处读枚举值、一处读子项数量。这不是设计余量，是没对齐。

三根轴的价值本该是「正交、能各自回答一个问题」。现在其中一根与另一根重合，  
还额外生出一个自相矛盾的判法。这部分不是「不该做复杂」，是**做复杂了却没做到复杂该有的干净**。

## 三、我的建议（只到概念层，不谈怎么改）

一句话：**从「三个能各自取值的轴」回到「一个显式枚举 + 可空属性 + 父子关系」**——  
也就是用户 11-22 提出的那个形状。但我和原始提议有一处不同，必须说清楚，不能含糊：

我不主张把「容器」「每天」「不判成败」都塞进类型枚举当取值。它们不是「另一种事情」，  
是同一条记录上的**关系**或**待遇**。所以收完之后应该是：

- 一个平铺枚举，列出这个软件里**现在真有的**几种事情（定日 / 定点 / 只有截止日，以及将来真出现的第 N 种）；
- 其余信息都是可空属性，按需填：截止日、时间、估时、重复声明、不判成败声明……
- 层级不占枚举取值，交给 `ParentTaskId` 自引用。

### 三条硬约束，一条都不能退

1. **形态必须显式存。** 11-21 那次 18 条误判，根子是靠 `StartAt == null` 猜形态，  
   不是因为用了枚举。这条是拿事故换的，退回去就是把事故还回来。
2. **容器是关系，不是类型值。** 它本来就不该出现在「枚举有哪几个值」这个问题里。
3. **判成败是读出来的，不是存进去的。** 「暂时不判」由截止日和今天算，  
   存成字段就会和 `DueAt` 打架；这条设计省掉了一个会打架的字段，成立。  
   （`VerdictMode.Never` /「守住」的存废另说，见第六节。）

### 一个不能省的说明

**这不是推翻重做。** 现在库里本来就是 `Shape` 一列主形态 + 两列独立取值，  
「每天」「不判成败」在 AI 动作里本来就是两个 bool 开关。要收的主要是**叙事和心智模型**：  
不再把它们讲成三根能自由组合的坐标轴，清掉空转取值和重复计数维度。  
已经落地那些读判据一行都不用白干。

## 五、顺带把 A 轮那个问题答了（仍是方向，不是定案）

A 轮要定的是：「大任务」和「阶段」，是同一类东西的两个层级，还是两类性质不同的东西？

既然容器是**关系**而不是类别，答案方向就浮出来了：  
**它们是同一套递归结构里的不同位置，不是两个类型。**

- 没有父容器的，叫大任务（顶层；截止日 / 归档 / 颜色是「在最上面」带来的，不是「另一类」带来的）；
- 有父容器的，叫阶段；阶段还能再挂阶段；
- 只有叶子会被完成、进今日清单、进完成率；
- 用户 11-21 举的「参加数学竞赛 → 学第一章 → 基本知识 / 做题 / 真题」就是这同一套结构。

由此，老 `projects` 表与 `items` 里 `ByChildren` 容器「两套壳」的问题也有了方向：  
不是两种东西，是**同一个关系被实现在了两处**。

但 A 轮当时留的那个判断题仍在，且只有用户能定：  
「大任务」是不是比「阶段」多一层意思——**一件我答应自己要了结、做完会归档的事**，  
而阶段只是拆的时候临时分的组？若是，顶层就还背着「目标」的身份，不能纯当位置看。  
这一条我不替他拍。

**也正因如此，下一步不是把分类表画得更完美，而是先定「这个软件里到底有几件事」。**  
那份清单我列不出来，只有用户知道自己用的时候卡在哪。
