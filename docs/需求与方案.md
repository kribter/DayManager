# DayManager 需求与方案

> 目标：一个知道自己真实状态、在关键时刻拉你一把的日程伙伴。
> 它不是日历，也不是时间统计工具，是**对抗逃避的执行系统**。

---

## 一、真实问题

表面诉求是"多端日程管理"，实际要解决的链条是：

```
计划过多 → 完不成 → 挫败 → 逃避（刷视频/打游戏）→ 更不想开始 → 回到计划过多
```

两条失败路径：

1. **执行层**：知道该做什么，但启动不了。一坐下就进入"脑袋空空"的低负荷娱乐状态。
2. **规划层**：高估自己能做的事，安排必然完不成，失败后挫败感加剧逃避。

已验证无效的手段：删除手机上的 B 站**不能阻止玩手机**——替代品是无限的（公众号、游戏、短视频）。
结论：**封杀某个 App 没有意义，真正要干预的是"我决定去娱乐"这个动作本身。**

---

## 二、产品形态（2026-10-26 定稿）

一句话：**AI 对话是这个软件的核心，另外三个界面是它的手和眼睛。**

| # | 界面 | 干什么 | 和 AI 的关系 |
|---|---|---|---|
| 1 | **对话** | 唯一「什么都能操作」的地方：聊着聊着就把事办了 | 它能读、能改日程 / 大任务 / 干预设置 |
| 2 | **日程** | 某一天的清单，能翻到任意一天；自己增删改查、改状态 | AI 写出来的东西落在这里 |
| 3 | **大任务** | 项目层：名字、截止日、进度、拆出来的子任务 | AI 拆出来的结构落在这里 |
| 4 | **时间** | 时间花在哪了（日 / 周 / 月 / 年）+ 干预设置 + 我的画像 | 是 AI 判断「你现在什么状态」的依据 |

> **为什么时间、干预、画像挤在一个界面**：它们本来就是同一件事的三个面——
> **数据**（时间花在哪）→ **判断**（画像：你是什么样的人）→ **行动**（干预：什么时候拦你）。
> 拆成三页的后果是改干预设置时看不到自己上周的数据，只能凭感觉调。放一起才能真正调得动。

### 2.1 为什么「拆解」不再占一个 Tab

第一版把「拆解」做成了独立的一页（输入框 + 参数 + 按钮）。它是验证 AI 能力用的脚手架，
但副作用是**把 AI 关进了一个「只能拆任务」的格子**——而这次定的目标是它能管所有东西。

拆解应该在对话里自然发生：

```
我：两周内把开题报告弄出来
AI：我先这么理解——（复述）……有两件事得先确认：
    ① 我猜你现在手头有数据了，对吗？
    ② 我猜每天能给它 1 小时，够吗？
我：数据还没有；每天 1 小时差不多
AI：（给出摊到 10 天的安排，每天一条，最长的那条 90 分钟）
    第 4 天那条可能卡住，我放在了上午。要写进日程吗？
我：写吧
```

多天的安排确实需要一整屏来看，所以结果子页保留，改由对话唤起。

### 2.2 任务状态：五态（关键在「跳过」和「放弃」的区别）

| 状态 | 值 | 含义 | 明天还出现吗 |
|---|---|---|---|
| 未开始 | `pending` | 默认 | 出现 |
| 进行中 | `in_progress` | 记 `started_at` | 出现 |
| 已完成 | `done` | 记 `completed_at` | 当天可见，之后不再出现 |
| **已跳过** | `skipped` | 今天不做了，可填一句原因（生病 / 有事 / 被别的事占了） | **第二天照常回来** |
| **已放弃** | `abandoned` | 承认不做了 | **永不再出现** |

区分这两态的目的不是界面好看，是**让统计不失真**：

- 完成率分母 = `done` + `pending` + `in_progress` + `abandoned`，**跳过不计入**
  —— 你已经明确决定今天不做它，那天它就不该算数；硬算进去只会让完成率无故变低。
- 放弃计入分母：那是真的没做。
- 一条任务被跳过太多次 → 那是「这事可能根本不该做」的信号，交由 AI 主动提出来谈，
  而不是默默让它每天滚回来。

### 2.3 撤销：永久可撤，且不需要经过 AI

AI 会犯错，而且它的错是批量的（一次可能改十条）。所以：

- **每一个写操作都记 `action_log`，带修改前的完整快照**，撤回就是拿快照写回去
- **永久可撤**（用户 2026-10-26 定），日志量极小，不设过期
- **撤回入口在界面上，不在对话里**——不需要跟 AI 说「帮我撤回」，
  因为发现 AI 改错了的那一刻，最不想做的事就是再跟它聊一轮
- 撤回粒度按**批次**（AI 的一次动作 = 一个可撤单元），可以展开逐条撤
- 撤回冲突时提示而不是硬覆盖：目标在这之后又被改过（被你自己或 AI），
  要告诉你「这条在 X 时间又被改过，撤回会覆盖成当时的样子」，让你决定
- **AI 不能真删数据**，只能标记放弃——删掉就撤不回来了

### 2.4 大任务只是容器

- 大任务自己**没有完成按钮**，进度 = 子任务 `done` 数 / 总数，自动算
  ——两层都能打勾一定会出现「子任务都没做完、项目却显示完成」的矛盾，完成率也算不清
- 大任务页要能回答的问题：还剩几天、进度如何、**卡在哪一步**（最久没动的那条）、
  哪些子任务已经逾期
- 只有「归档整个项目 / 放弃整个项目」这种影响一片的动作才要二次确认

### 2.5 四个界面之间的流向

```
                    ┌──────────────┐
                    │   对话（核心）│
                    └──────┬───────┘
              读+写 ┌──────┼──────┐ 读
                    ▼      ▼      ▼
              ┌────────┐ ┌──────┐ ┌──────────────┐
              │ 日程   │ │大任务│ │ 时间/干预/画像│
              └────────┘ └──────┘ └──────┬───────┘
                    │                    │
                    └───── 实际用时 ─────┘
                            ↓
                     画像校准 → 回到对话
```

时间的流逝从右下方回流到对话：今天做了什么、花了多久、在哪个时段效率高——
这些是 AI 下一次排程的依据。没有这条回流，AI 只能凭你的主观估计排，
而主观估计正是「计划过多 → 完不成 → 挫败」这个循环的起点。

### 2.6 时间页里具体有什么

**① 时间使用**：日 / 周 / 月 / 年切换；按应用排行（B 站刷了多久）；趋势对比（这周比上周多还是少）。

**② 干预设置**：

| 设置项 | 默认值 | 说明 |
|---|---|---|
| 娱乐应用名单 | 手动标记一次即记住 | 不预设黑名单——替代品是无限的，名单的价值在于**你自己标过的那几个** |
| 单应用连续时长阈值 | 30 分钟 | 到了就触发情境判断（不是直接拦） |
| 每日娱乐总时长额度 | 待定 | 超了之后由 AI 决定怎么提醒，而不是弹一个无脑警告 |
| 免打扰时段 | 待定 | 例如 22:00 之后不再打扰 |
| 「今天别再提了」 | 弹窗上常驻 | **赦免权**：没有这个出口，软件会沦为骚扰工具，结局是被关掉 |

**③ 我的画像**：可见、可编辑。

> 为什么画像必须看得见、能改：AI 误解了你却没地方纠正，它会一直错下去，
> 而你甚至不知道它为什么老给你排这么多。画像写死在黑盒里 = 把校准的机会堵死。
>
> 画像里哪些是算出来的、哪些是聊出来的，界面上要标清楚：
> 作息与高效时段**算**出来（从使用时长推断），可以用对话修正；
> 「AI 对你的理解」是一段纯文本，**你直接改**。

**采集端的现实差异（Windows 先做，Android 模型先行）**：

| 平台 | 能拿到什么 | 状态 |
|---|---|---|
| Windows | 应用名 + **窗口标题**（`GetForegroundWindow` + `GetWindowText`，P/Invoke） | 本期做 |
| Android | 只能到包名 / 应用名（`UsageStatsManager`）；窗口标题要 Accessibility Service，代价过大 | 代码不做，**数据模型与接口按两端通用设计**（`usage_sessions` 已有 `device_id` / `platform`） |

### 2.7 参数是活的：AI 持续校准，不是设一次就固定

用户 2026-10-26 定：**默认值、AI 的行为与安排，都要随用户变化动态调整，实现自适应。**

也就是说，这个软件里**不存在"设一次就固定"的旋钮**——只有冷启动的起点值，之后由 AI 接管校准。
界面上的设置项仍然在（可以手动改、可以覆盖 AI），但它显示的是"当前值 + 它是怎么来的"，
而不是一个等待你填写的空框。

**交给 AI 自己调的：**

| 参数 | 起点 | 校准依据 |
|---|---|---|
| 一件事每天的上限 | 120 | 最近 N 天**实际完成量**（不是用户自报） |
| 排程保守系数 | 0.8 | 历史 `estimate_minutes` 与 `actual_minutes` 的比值 |
| 干预阈值（单应用连续时长） | 30 分钟 | 用户对干预的实际反应（秒关继续玩 / 真的切走） |
| 干预强度与频率 | 中 | 「今天别再提了」被点掉的次数 |
| 主动消息时机 | 早晨 + 晚间 | 用户真正回复的时段 |
| 语气与说话方式 | 温和鼓励 | 连续低完成率转严肃；哪种方式有反应就用哪种 |

> **口径（2026-10-27 用户澄清；实现时一度理解反了，特地记在这里）**
>
> 「一件事每天的上限」是**给这一件事的额度**，不是他一天的总容量。
> 他当天原有的安排不占这里的额度——**两件事各占两小时，不等于他一天只有两小时。**
> 上面 2.1 那段原始对话里写的是"我猜每天能**给它** 1 小时"，用词本来就是对的，
> 是落到实现时把"给它"读成了"总共"，于是当天有别的事时，
> 新拆的这件事被压到几乎排不进去。
>
> 那"一天排太满"靠什么防？**靠 AI 看当天已排的内容后提出异议**（它看得到往后七天的清单），
> 而不是用一个固定总数卡着。用一个数防过载，代价是每件事都被削平——
> 明明能给两小时的事，只因为当天还有别的，就被压成 40 分钟，
> 而那件别的事其实一点没少。削平不是保护，是让所有事都做不动。

**不交给 AI 的（用户主权，改之前必须问）：**

- 免打扰时段的**硬边界**（AI 可以建议，不能自己挪）
- 「今天别再提了」赦免权**本身**是否存在
- 数据采集的边界（哪类应用不采集）

#### 四个必须守住的约束，否则动态调参会慢慢失控

1. **冷启动必须有起点。** 没有数据时用保守默认值，AI **不许在没数据的情况下调参**——
   那不叫自适应，叫瞎猜。
2. **一次只调一个参数，且有观察窗口（建议 7 天）。** 同时调三个，就算生效了也不知道是哪个起的作用。
3. **调整幅度有上限，且守住基线。** 完成率低 → 降额度；若无下限会一路降到 0，
   那时「完成率 100%」毫无意义。
4. **必须告知 + 可回滚。** AI 改了什么、依据是什么，要说出来；走 `action_log`，一键撤回。
   **静默调参的后果是用户觉得软件时好时坏、莫名其妙**，最后不信任它。

#### 最大的陷阱：完成率是一个会被参数操纵的指标

AI 把每天额度调低 → 完成率上升 → 它以为自己调对了 → 继续调低。
**指标在变好，用户在变差**——而且这个循环自己看不出问题，因为每一步都"有数据支持"。

所以校准必须盯**绝对锚点**：

- 主锚点：每周实际完成的任务数、实际投入的分钟数（这些不会被参数稀释）
- 完成率**只用来判断"排得合不合理"**，不能用来判断"人有没有变好"

#### 收敛节奏

前两周**只观察不调**（积累基线）；第三周起小幅调，一次一个，7 天一轮。

> 需要说清楚的限度：单用户、每天只有一个数据点，7 天窗口在统计上很脆弱。
> 这不是严谨的优化，是**"有依据的猜测 + 可回滚"**。别把它包装成能自动收敛的系统——
> 它的价值在于方向大致对且永远可撤，不在于精确。

#### 实现上的硬要求

策略**必须存在数据库里**（`policy_settings` 表），不能只活在对话上下文里：
AI 每次被唤起都要带上当前策略，否则不同次调用会给出互相矛盾的安排。

### 2.8 批量修改：交给 AI，不做多选界面

用户问：用户自己会不会也需要批量修改？是不是干脆都让 AI 批量改？

**判断：不做通用的多选界面（长按多选 + 批量工具栏），只保留一个确定性快捷操作。**

1. 用户脑子里那些"批量"，几乎全部能用一句话说清楚：
   「今天没做完的都推到明天」「把这个项目的任务全往后推一周」「想做的那几条先撤了」。
   **为它们专门做一套多选 UI，是在用重量级的方案解决一个已经被更轻地解决了的问题。**
2. **让 AI 批量 = 同时拿到了批量能力和撤回能力。** AI 的写操作天然带 `action_log`，
   可以整批撤回；手写的批量 UI 还得自己再接一套撤销——工作量在，风险也在。
3. 自用的单用户界面，多选模式（进入 / 退出、全选、反选、批量工具栏）是一大块交互成本，
   而它服务的场景一个月可能只出现几次。

#### 一个手动快捷也不留（2026-10-26 定）

原本打算保留「今天没做完的 → 推到明天」一个按钮，最后决定**不留**：
既然定了 AI 是核心，凡是「改一批」的事就统一走对话，不另开一条绕过 AI 的路。
规则越少越好记；而且不留这个口子，就不会出现「有的批量能撤、有的不能撤」这种不一致。

代价是认账的：

- **AI 不可用（断网 / 后端没起来）时，批量改期只能一条条改。**
  离线本来就是只读，所以这不算新增损失。
- 这个高频动作每次要等 AI 二三十秒。**如果实际用起来嫌慢，
  就在对话页预置一句常用指令（点一下填好「把今天没做完的推到明天」，仍然走 AI），
  而不是退回手写批量按钮**——退回手写按钮等于把撤回能力也一起丢了。

#### 批量之后的通知必须够醒目

AI 一次改 3 条以上时，通知里要能展开看到**每一条**，并给一个「全撤」按钮。

不改「乐观更新」的基调（不做事前确认），但一次改十条却只说一句「已更新」，
用户根本来不及看清改了什么——那不叫乐观，叫敷衍。

#### 「这几条」在对话里怎么指（暂不解决，等 M5 再说）

先靠自然语言：AI 有完整的日程上下文，「把早上那三条推到明天」它听得懂。

曾想在日程页每条的「更多」菜单里加一项「拿去问 AI」，**不做**：

1. 菜单里已经有改状态 / 重命名 / 删除，再塞一项就杂了；
2. 更根本的是，**「就这条说点什么」跟「删除」「重命名」不是一类动作**——
   前者是开口说话，后者是改数据。混在一个菜单里，性质都不对。

**等 M5 对话页做完，如果实际用起来真的出现「说不清是哪一条」的情况，
再在对话输入框里加 `@` 引用**（打 `@` 弹出今天的条目供选择）。
放在输入框里，既不占菜单，也贴合「看到一条 → 想就它说点什么」这个动作本身。
现在不做，是因为这个需求**还没被真实验证过**——没验证就先别建。

## 三、决定产品设计的六条洞察

1. **干预点在"打开娱乐应用的那一秒"，不在事后报表。** 统计类工具的通病是新鲜三五天后免疫。
2. **没有具体时间的待办必然被拖。** "等下再做"没有终点，必须强制落到时间段。
3. **回顾界面不能是指责式的。** "今天摸鱼 6 小时"只会加重挫败 → 更想逃避。默认只展示"做到了什么"。
4. **瓶颈是启动，不是遗忘。** 用户明确知道自己该做什么。设计目标是降低启动摩擦力，而不是把待办推到眼前。
5. **AI 必须被授权说"不"，但方式是对话式的。** 提出异议 + 给理由 + 等二次确认，绝不擅自拒绝（因为有时是用户低估了难度，有时是真的要做）。
6. **使用时长数据的真正价值是"校准"，不是"审判"。** 它用来算出你真实的可用时间和做事速度，让 AI 排出不会失败的计划。

## 四、需求分层

### P0 最小可用（能跑起来就用）

- 统一记录：日程（有时间段）与待办（有截止日）同一张表、同一套界面
- **强制时间化**：进"今天"的条目必须有时间段，否则不能进今日清单
- 日视图 + 今日清单 + 增删改查
- 完成打勾 + 完成时的正反馈
- Windows 端本地 SQLite 存储

### P1 抗拖延核心（产品的灵魂）

- **Windows 使用时长采集**（应用名 + 窗口标题）
- **情境感知干预引擎**（见第六节）
- **启动辅助**：最小启动步骤 + "先做 10 分钟"计时
- **进行中状态 + 启动延迟统计**（量化拖延改善程度的核心指标）
- **项目层**（项目 → 任务两级结构，项目进度按子任务完成情况自动算出）
- 重复日程（RRULE 展开，用 Ical.Net）
- 跨端同步：Windows ↔ Android

### P2 AI 伙伴

- 对话式增删改查日程（先确认再执行）
- 排程建议 + 防过量异议机制
- 状态感知（生病、疲惫时主动减负）
- 每日总结：先肯定做到的，再给建议
- 语气随状态切换

### P3 远期

- 月视图 / 年视图（每天 / 每月完成情况概览，12 个月色块）
- 大目标分解（把项目拆成任务树）
- 用户画像（用确定性统计，不用 LLM 生成空话）

## 六、干预引擎（产品核心）

不是无脑拦截，是**情境感知的双向响应**：

| 情境 | 判定依据 | 响应 |
|---|---|---|
| 今日任务已全部完成 + 进入娱乐 | 剩余未完成数 = 0 | "今天的事做完了，好好休息" |
| 已连续工作较久 + 进入娱乐 | 连续专注时长 > 阈值 | "已经做了 90 分钟，该休息一下了" |
| 节假日 / 周末 + 进入娱乐 | 节假日日历 + 用户设定 | 放松模式，不打扰 |
| 仍有未完成 + 进入娱乐 | 剩余未完成数 > 0 | 温和提示："还有 3 件事，其中 X 只要 10 分钟" |

设计约束：

- **不阻断操作**，只弹提示，但必须点一下才消失（增加摩擦力）
- 提示内容永远是"给一个更小的起点"，不是"你怎么又在玩"
- 同一会话有冷却时间，避免反复弹窗变成骚扰

额外轻量触发（成本极低、可能很有效）：

- 电脑从睡眠/锁屏唤醒时 → 极简提示："今天还剩 3 件事，先挑一个做 10 分钟？"
- 检测到连续使用娱乐应用超过 N 分钟 → 触发上表判断

### 启动辅助（解决"知道该做但不想动"）

- 每条任务可填 **最小启动步骤**（如"写报告" → "打开文档写个标题"）
- 一键 **"先做 10 分钟"** → 计时器启动，降低心理承诺
- 10 分钟结束时询问继续还是结束，结束时无论是否做完都给正反馈

## 七、AI 行为准则

| 维度 | 规则 |
|---|---|
| 性格 | 日常温和鼓励；检测到连续多天完成率偏低时切换到严肃督促 |
| 防过量 | 用户排任务过多时**提出异议 + 说明依据**（历史实际速度）+ **等待二次确认**，不擅自拒绝 |
| 状态感知 | 从对话中提取状态（感冒、累、心情差）→ 主动建议减少当日安排 |
| 日总结 | 先说做到的，再说没做的；建议必须具体可执行 |
| 安全 | **乐观更新**：直接执行 + 通知 + **永久可撤回**（记入 `action_log`，界面上有独立撤销入口，不需要跟 AI 说）；**AI 不能真删数据**，只能标记放弃 |
| 排程依据 | 用 `actual_minutes` 的历史均值校准，不用用户的主观估计 |
| 调参 | 参数是活的（见 2.7）：可自己调的据数据调，**一次一个、7 天一轮、有上下限**；用户手改过的不再自动覆盖；**每次调整必须说明依据并可回滚**；校准盯绝对产出量，不盯完成率 |
| 安全红线 | **API key 绝不能打进客户端**，所有 AI 请求走自建后端代理 |

### 10.2 由答复推导出的设计决定

1. **AI 写操作 = 乐观更新 + 永久可撤回**（2026-10-26 改为永久，原为 24 小时）。
   必须有完整的 `action_log` 支持一键回滚，撤回入口在界面上而非对话里；
   删除走软删除墓碑，因此删除也可撤回。
2. **区分两种场景**（互不冲突）：
   - 用户自己排任务过多 → AI 提出异议 + 给理由 + **等二次确认**
   - AI 主动调整日程 → 自动执行 + 通知 + 可撤回
3. **作息信息不要求手工填表**：优先从使用时长数据自动推断（最后活跃时间→入睡时间、
   各时段完成率→高效时段），再用对话补充修正，结果存入 `user_profile`。
4. **本机作服务器要解决外网访问**：家用宽带通常没有公网 IP，建议用 Tailscale（免费、
   近乎零配置）做内网穿透，手机在外面也能同步。本机需设为不休眠 + 开机自启托盘常驻。
5. **干预必须提供"赦免权"**：弹窗上要有「今天别再提了」选项，点了当天不再干预。
   没有这个出口，软件会沦为骚扰工具，结局是被用户关掉。
6. **AI 主动触发规则（初版建议）**：早晨计划确认、日程开始前提醒、未完成任务 + 进入娱乐时干预、
   晚间日总结、连续多天低完成率时主动严肃对话。

### 10.4 第三轮：主流程与排程设计（2026-10-26）

用户提出的主流程：**给 AI 一批任务清单 → AI 问清所需信息 → 拆解 → 排出每日计划（可到时间）→
完成给正反馈 → 出情况时动态调整**。

对照现有文档，其中「拆解」（P3）、「排时间」（洞察 2 + P0 强制时间化）、「正反馈」（M6）、
「动态调整」（P2 状态感知）均已存在。本次确认的是下面这些此前没有的部分。

| # | 新增决定 | 说明 |
|---|---|---|
| C1 | **「想做的事」与「该做的事」并列** | 两类任务放同一个列表。逃避的本质是「该做的」永远还不完、「想做的」永远排不上，于是靠娱乐补偿。并列之后 AI 才能给出真正的奖励：做完该做的，主动把想做的顶上来 |
| C2 | **排程的保守程度是生死线，拆解的智能程度只是加分项** | 排乐观了，AI 就变成一个比用户更会高估、还带权威感的计划者，失败时的挫败感比自己排更重（「连 AI 排的都做不到」） |
| C3 | **拆解粒度下限：单条 ≥ 25 分钟** | 拆太碎（每条 5 分钟）打勾变成走过场，失去成就感；要卡在「做完有感觉」的尺度 |
| C4 | **信息收集用「猜 + 改」，不用问答** | AI 先给一版带明确猜测的计划（「我猜要 3 小时，放上午，对吗？」），让用户改而不是填。来用这个软件的人本来就不想想这些，连问 8 个问题会直接劝退。也符合 B8 的乐观更新基调 |
| C5 | **Windows 端先跑出完整闭环，Android 后置** | 先把一端用起来，验证闭环有效再铺第二端 |

#### 排程的两个失效模式（比「一天排太多」更真实）

原先担心的「拆成 30 条 → 今日清单爆炸」**不成立**：有截止日期且摊开排，30 条分 10 天就是每天 3 条。
真正的风险在另外两处：

1. **欠账滚存**。今天 3 条没做完 → 明天 6 条 → 后天 9 条。累积到十几条时人的反应不是「慢慢补」，
   是「这个项目废了」——直接接回第一节「开摆」那一环。
   - 顺延要有上限：每天最多补 1-2 条欠账，其余往后挤而不是全搬过来
   - 连续欠账超阈值 → AI 主动**重新协商**（延期 / 砍范围），不是催促
   - 心态定位：**欠账是信号（说明排错了），不是债务（说明你不行）**
2. **学生综合症**。摊得越均匀，越容易被「反正还有 9 天」消解。
   所以均匀摊开的计划需要一个「为什么今天就得做这几条」的理由——
   例如把最难 / 最不确定的放最前面，或今天做完明天可休一天。

#### 依赖约束（决定实现顺序）

- 第七节已定：「排程用 `actual_minutes` 历史均值校准，不用用户主观估计」。
  而 `actual_minutes` 要等 M3（Windows 使用时长采集）才有数据。
  **结论：AI 自动排时间必须排在 M3 之后；但「拆解 → 执行 → 正反馈」不依赖 AI、也不依赖时长数据，可以提前。**
- 先做手动版（自己拆、自己排时间、完成后给反馈）验证闭环；
  **如果手动版自己都用不起来，AI 版大概率也救不了。**
- AI 调用必须走自建后端代理（安全红线），因此 API 服务是 AI 能力的唯一入口。


### 10.5 第四轮：产品形态定稿（2026-10-26 晚）

用户提出：核心是 AI 对话（一个界面），另外三个界面分别是日程、大任务、时间使用；
AI 应能访问并管理软件里的所有内容。

| 编号 | 问题 | 决定 |
|---|---|---|
| D1 | 界面结构 | **四个界面**：对话（核心）/ 日程 / 大任务 / 时间（含干预设置 + 画像） |

| D3 | 大任务 | **只是容器**，自己不能打勾，进度按子任务自动汇总 |
| D4 | 撤回 | **永久可撤**，界面上有独立入口，**不经过 AI**；按批次撤；冲突时提示而非硬覆盖；**AI 不能真删数据** |

| D6 | 平台顺序 | Windows 先做；Android 数据模型与接口先行，采集代码等真机 |
| D7 | 「拆解」页 | **并入对话**；多天安排的结果子页保留，由对话唤起 |
| D8 | 参数默认值 | **不存在固定默认值**：只有冷启动起点，之后由 AI 持续动态校准；界面显示"当前值 + 它是怎么来的"；用户手改过的项 AI 不再自动覆盖 |
| D9 | 对话上下文 | **跨天延续**（不延续就了解不到实时情况）；历史滚动压缩进 `daily_context`，防止上下文无限增长 |
| D10 | 批量修改 | **不做多选 UI，也不留任何手动批量按钮**：批量需求全部交给 AI 一句话完成（顺带天然拿到撤回能力）。代价：AI 不可用时只能一条条改（离线本就只读，可接受） |
| D11 | 「拿去问 AI」入口 | **不做**。它跟删除 / 重命名不是一类动作，塞进「更多」菜单只会让菜单变杂。等 M5 后若真出现指代困难，再加输入框里的 `@` 引用 |
| D12 | 启动后落在哪个界面 | **默认「对话」**（用户 2026-10-26 定），**可由用户改**并存为偏好；属用户主权，AI 不自动调 |
| D13 | 项目进度的分母 | **不含已放弃的子任务**（与完成率的口径不同，见下）。目的是让进度条能走到 100% |
| D14 | AI 拆解必须带 `project` | **硬性要求**。不带的话子任务散在日历里，没有任何地方显示「这件事做到哪了」——做完三条也感觉不到自己在推进 |
| D15 | 对话记录必须落地 | 存 `chat_messages`（含 `batchId`、`outcomesJson`、`IsUndone`）。**系统提示不入库**（那是本次运行的状态，不是对话内容）。清空是软删，误点可恢复 |
| D16 | AI 不按 JSON 回的时候怎么办 | **先截取 JSON 片段重试，仍失败就把它说的话当回复，而不是报错**。并在提示词末尾再强调一次格式（模型对靠后的指令权重最高） |
| D17 | AI 的思考不能出现在回复里 | JSON 增加 `think` 字段作草稿纸（后端读完即丢），提示词明确"想法写在 think，reply 只写你说的那句话"。**兜底**：回复里出现 `actions`/`suggestions` 等系统字段名即判为泄漏并剔除（用户不知道这些概念，出现即 100% 泄漏；改名前用的 `questions` 仍在名单里，模型可能还记得）。**绝不用 `reasoning_content` 顶替空回复** |

#### D13 为什么和完成率的口径不一样（这是刻意的，不是笔误）

完成率的分母**包含** `abandoned`（放弃是承认失败，必须计入）。
项目进度的分母**排除** `abandoned`，因为它回答的是另一个问题："这件事还剩多少要做"。

一条已经明确不做了的子任务不属于"还要做"的部分。算进去的后果很具体：
一个做了八条、放弃两条的项目，进度条永远卡在 80%，看着像永远做不完——
而"永远做不完的进度条"正是这个软件要消灭的那种挫败感。

放弃了几条单独记着，界面上写成"3 / 8 件完成（放弃 1 件）"，信息一个不少。

#### D14 的实测结论

这条是 2026-10-27 补上的：`AiAction.Project` 字段早就声明了，但 `ItemTools` 从没用过它，
于是 AI 拆出来的任务全都没有项目归属，大任务页对 AI 建的任务是空的。
补上之后实测：说一句"两周内把数据结构期末复习弄出来"，
AI 拆 8~9 条，每条都挂到同一个项目下，第二次拆同名事件会复用同一个项目（不会每拆一次多建一个）。

#### D16 的实测经过（2026-10-27）

对话记录落地之后第一次实测就撞上了：
用户说"你只要回一句话确认收到"，模型就真的只回一句中文，一个括号都没给——
哪怕 API 层已经开了 `response_format: json_object`。

这不是配置错误（参数确认发出去了），是模型在"听用户的话"和"守输出格式"之间选了前者。
而真实使用中"只要一句话""别整格式"这种说法会经常出现，所以它必然再次发生。

三层处理，按代价从小到大：

1. **格式要求放在最后再说一遍**：系统提示写在最前面，聊过几轮之后约束力明显下降。
   在 messages 末尾补一条 system 提醒（只发给模型，不进对话记录）之后，
   实测同一个问题，AI 正确回答了"你让我记的是：你最容易在打开电脑后刷视频"。
2. **解析失败先截取**：模型偶尔会在 JSON 前后加一句"好的，结果是："，
   截出中间那段 `{...}` 再解析一次就能救回来。
3. **仍失败就当纯回复**：它只是在聊天，本来也没有要执行的动作。
   报一句"AI 返回的不是 JSON"会把明明有内容的一轮变成故障提示——
   用户会以为 AI 挂了，而实际上它说话了。

#### 本轮主动提出、并被采纳的两处架构问题

1. **「拆解」不该占一个 Tab。** 它把 AI 关进了「只能拆任务」的格子，
   与「AI 能管所有东西」直接冲突。真正合理的形态是：拆解在对话里发生。
2. **AI 要能管理所有内容，就不能只活在客户端里。** 现有链路是
   「后端只代理模型、真正读写数据库的是客户端」，放到下面三个场景会全部撞墙：
   AI 主动提醒（客户端关着时触发不了）、手机端、常驻服务。
   所以后端要从「AI 代理」升级为「AI + 数据接口」，客户端退化为显示层 + 手动操作层。
   **这个越早改越便宜**：现在改是半天，等四个页面写完再动是重写。
