# DayManager 需求与方案

> 目标：一个知道自己真实状态、在关键时刻拉你一把的日程伙伴。
> 它不是日历，也不是时间统计工具，是**对抗逃避的执行系统**。

---

## 一、真实问题

表面诉求是"多端日程管理"，实际要解决的链条是：

```
计划过多 → 完不成 → 挫败 → 逃避（刷视频/打游戏）→ 更不想开始 → 回到计划过多
```

两条失败路径：

1. **执行层**：知道该做什么，但启动不了。一坐下就进入"脑袋空空"的低负荷娱乐状态。
2. **规划层**：高估自己能做的事，安排必然完不成，失败后挫败感加剧逃避。

已验证无效的手段：删除手机上的 B 站**不能阻止玩手机**——替代品是无限的（公众号、游戏、短视频）。
结论：**封杀某个 App 没有意义，真正要干预的是"我决定去娱乐"这个动作本身。**

---

## 二、决定产品设计的六条洞察

1. **干预点在"打开娱乐应用的那一秒"，不在事后报表。** 统计类工具的通病是新鲜三五天后免疫。
2. **没有具体时间的待办必然被拖。** "等下再做"没有终点，必须强制落到时间段。
3. **回顾界面不能是指责式的。** "今天摸鱼 6 小时"只会加重挫败 → 更想逃避。默认只展示"做到了什么"。
4. **瓶颈是启动，不是遗忘。** 用户明确知道自己该做什么。设计目标是降低启动摩擦力，而不是把待办推到眼前。
5. **AI 必须被授权说"不"，但方式是对话式的。** 提出异议 + 给理由 + 等二次确认，绝不擅自拒绝（因为有时是用户低估了难度，有时是真的要做）。
6. **使用时长数据的真正价值是"校准"，不是"审判"。** 它用来算出你真实的可用时间和做事速度，让 AI 排出不会失败的计划。

## 三、需求分层

### P0 最小可用（能跑起来就用）

- 统一记录：日程（有时间段）与待办（有截止日）同一张表、同一套界面
- **强制时间化**：进"今天"的条目必须有时间段，否则不能进今日清单
- 日视图 + 今日清单 + 增删改查
- 完成打勾 + 完成时的正反馈
- Windows 端本地 SQLite 存储

### P1 抗拖延核心（产品的灵魂）

- **Windows 使用时长采集**（应用名 + 窗口标题）
- **情境感知干预引擎**（见第五节）
- **启动辅助**：最小启动步骤 + "先做 10 分钟"计时
- **进行中状态 + 启动延迟统计**（量化拖延改善程度的核心指标）
- **项目层**（项目 → 任务两级结构，项目进度按子任务完成情况自动算出）
- 重复日程（RRULE 展开，用 Ical.Net）
- 跨端同步：Windows ↔ Android

### P2 AI 伙伴

- 对话式增删改查日程（先确认再执行）
- 排程建议 + 防过量异议机制
- 状态感知（生病、疲惫时主动减负）
- 每日总结：先肯定做到的，再给建议
- 语气随状态切换

### P3 远期

- 月视图 / 年视图（每天 / 每月完成情况概览，12 个月色块）
- 大目标分解（把项目拆成任务树）
- 用户画像（用确定性统计，不用 LLM 生成空话）

> 注：重复日程、Android 使用时长采集已按用户答复提前到一期范围，不再是远期项。

## 四、统一记录模型

核心表 `items`（日程与待办合一，用可空字段区分）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `uid` | uuid / text | 主键 / 跨端稳定标识 |
| `title` / `notes` | text | 标题、备注 |
| `start_at` / `end_at` | datetime | 时间段，**可空**（纯待办无此值） |
| `due_at` | datetime | 截止时间，可空 |
| `is_all_day` | bool | 全天标记 |
| `timezone` | text | 所属时区（跨时区正确性靠它） |
| `status` | text | `pending` / `in_progress` / `done` / `cancelled` |
| `started_at` | datetime | **首次开始时间**，与创建时间之差 = 启动延迟（核心抗拖延指标） |
| `completed_at` | datetime | 完成时间，统计必需 |
| `estimate_minutes` | int | 预估耗时 |
| `actual_minutes` | int | 实际耗时，**AI 排程校准的历史依据** |
| `minimal_step` | text | 最小启动步骤（2 分钟能做完的第一步） |
| `rrule` / `exdates` | text | 重复规则（RFC5545）+ 例外日期 |
| `recurrence_parent_id` / `original_start` | uuid | 重复日程"改这一次"的覆盖记录（**勿与项目层级混淆**） |
| `project_id` | uuid | 所属项目，指向 `projects` 表，可空 |
| `parent_task_id` | uuid | 父任务，可在任务下再挂一层子任务，可空 |
| `tags` / `priority` |  | 标签（可选）/ 优先级（高、中、低） |
| `reminders` | json | 提醒配置 |
| `version` / `updated_at` / `deleted_at` |  | 同步三件套：版本号、时间戳、软删除墓碑 |
| `device_id` | text | 最后修改的设备 |

其他表：

- `projects`：**项目层**（两级结构中的上层）
  `id` / `name` / `description` / `color` / `status`（active / archived）/ `target_date` / 同步三件套
  项目进度由子任务完成情况自动算出（`done` 数 / 总数），是正反馈与 AI 汇报的重要素材
- `usage_sessions`：设备使用会话（按会话聚合，非逐秒记录）
  `device_id` / `platform` / `app_id` / `app_name` / `window_title` / `start_at` / `end_at` / `duration_sec`
- `daily_context`：每日上下文
  `date` / `is_holiday` / `day_type`（工作日/周末/节假日）/ `ai_state_summary` / `daily_review`
- `ai_messages`：对话历史
- `ai_action_log`：AI 的每一次写操作，**必须支持撤销**

## 五、干预引擎（产品核心）

不是无脑拦截，是**情境感知的双向响应**：

| 情境 | 判定依据 | 响应 |
|---|---|---|
| 今日任务已全部完成 + 进入娱乐 | 剩余未完成数 = 0 | "今天的事做完了，好好休息" |
| 已连续工作较久 + 进入娱乐 | 连续专注时长 > 阈值 | "已经做了 90 分钟，该休息一下了" |
| 节假日 / 周末 + 进入娱乐 | 节假日日历 + 用户设定 | 放松模式，不打扰 |
| 仍有未完成 + 进入娱乐 | 剩余未完成数 > 0 | 温和提示："还有 3 件事，其中 X 只要 10 分钟" |

设计约束：

- **不阻断操作**，只弹提示，但必须点一下才消失（增加摩擦力）
- 提示内容永远是"给一个更小的起点"，不是"你怎么又在玩"
- 同一会话有冷却时间，避免反复弹窗变成骚扰

额外轻量触发（成本极低、可能很有效）：

- 电脑从睡眠/锁屏唤醒时 → 极简提示："今天还剩 3 件事，先挑一个做 10 分钟？"
- 检测到连续使用娱乐应用超过 N 分钟 → 触发上表判断

### 启动辅助（解决"知道该做但不想动"）

- 每条任务可填 **最小启动步骤**（如"写报告" → "打开文档写个标题"）
- 一键 **"先做 10 分钟"** → 计时器启动，降低心理承诺
- 10 分钟结束时询问继续还是结束，结束时无论是否做完都给正反馈

## 六、AI 行为准则

| 维度 | 规则 |
|---|---|
| 性格 | 日常温和鼓励；检测到连续多天完成率偏低时切换到严肃督促 |
| 防过量 | 用户排任务过多时**提出异议 + 说明依据**（历史实际速度）+ **等待二次确认**，不擅自拒绝 |
| 状态感知 | 从对话中提取状态（感冒、累、心情差）→ 主动建议减少当日安排 |
| 日总结 | 先说做到的，再说没做的；建议必须具体可执行 |
| 安全 | 所有写操作先给确认再执行，且记入 `ai_action_log` 支持撤销 |
| 排程依据 | 用 `actual_minutes` 的历史均值校准，不用用户的主观估计 |
| 安全红线 | **API key 绝不能打进客户端**，所有 AI 请求走自建后端代理 |

## 七、技术选型（已定）

| 层 | 选型 | 理由 |
|---|---|---|
| 客户端 | .NET MAUI（C# + XAML） | 一套代码覆盖 Windows（WinUI 3）与 Android |
| 本地存储 | SQLite + EF Core | 两端共用同一套模型 |
| 后端 | ASP.NET Core Minimal API | 与客户端统一 C#，同时作为 AI 网关 |
| 数据库 | SQLite 起步，后续可换 PostgreSQL | 个人自用数据量极小 |
| 重复规则 | Ical.Net | 别自己造 RRULE 轮子 |
| 时区 | Noda Time | 跨时区正确性 |
| AI | 云端 API（DeepSeek / 通义等），走后端代理 | 个人用量成本极低 |
| 提醒 | 本地闹钟（Android）+ 系统通知（Windows） | 国内 Android 无 Google 服务，FCM 不可用；一期不做服务端推送 |

版本基线：.NET 10 / MAUI 10（注意 MAUI 支持窗口较短，需跟随年度大版本升级）。

## 八、里程碑（已按战略价值重排）

Windows 使用时长采集**提前**，因为它是干预引擎和 AI 排程的输入，不是可有可无的统计功能。

| 阶段 | 内容 | 产出 |
|---|---|---|
| M0 | .NET 10 + MAUI 项目骨架，SQLite 打通 | Windows 上能跑起来 |
| M1 | 统一记录 CRUD + 强制时间化 + 日视图 | 可以开始用了 |
| M2 | 后端同步服务 | 两端数据打通的基础 |
| M3 | Windows 使用时长采集（应用名 + 窗口标题） | 真实数据开始积累 |
| M4 | Android 端 + Android 使用时长采集 | 两端覆盖 |
| M5 | 情境感知干预引擎 | **产品核心价值落地** |
| M6 | 启动辅助 + 完成正反馈 + 每日回顾 | 抗拖延闭环成形 |
| M7 | AI 对话操作日程（后端代理 + 确认机制） | AI 接入 |
| M8 | AI 排程校准、日总结、语气切换 | AI 成为真正的伙伴 |
| M9+ | 月/年视图、重复日程、大目标分解、画像 | 打磨期 |

数据模型从 M1 就把 `rrule`、`actual_minutes`、`minimal_step` 等字段预留好，避免后期改库。

### 9.2 由答复推导出的设计决定

1. **AI 写操作 = 乐观更新 + 可撤回**。必须有完整的 `ai_action_log` 支持一键回滚，
   撤回时限建议 24 小时；删除走软删除墓碑，因此删除也可撤回。
2. **区分两种场景**（互不冲突）：
   - 用户自己排任务过多 → AI 提出异议 + 给理由 + **等二次确认**
   - AI 主动调整日程 → 自动执行 + 通知 + 可撤回
3. **作息信息不要求手工填表**：优先从使用时长数据自动推断（最后活跃时间→入睡时间、
   各时段完成率→高效时段），再用对话补充修正，结果存入 `user_profile`。
4. **本机作服务器要解决外网访问**：家用宽带通常没有公网 IP，建议用 Tailscale（免费、
   近乎零配置）做内网穿透，手机在外面也能同步。本机需设为不休眠 + 开机自启托盘常驻。
5. **干预必须提供"赦免权"**：弹窗上要有「今天别再提了」选项，点了当天不再干预。
   没有这个出口，软件会沦为骚扰工具，结局是被用户关掉。
6. **AI 主动触发规则（初版建议）**：早晨计划确认、日程开始前提醒、未完成任务 + 进入娱乐时干预、
   晚间日总结、连续多天低完成率时主动严肃对话。
